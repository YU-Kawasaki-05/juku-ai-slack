# Phase 2 提案（2026-08-02 リリース準備時点）

>
> 前提: 現行のジョブ実行基盤は **Cron を使わない**（DEC-13）。バックグラウンド実行は Next.js の `after()`（`next/server`）。
> 以下の提案もこの基盤に統一する起動方式を選んでいる。
> ⚠️ 注記: DEC-13 が対象とするのは Slack への即時応答経路のみで、バッチ用 Cron 自体を禁じる決定ではない。

## 1. FR-08: AI 月次レポート自動生成

### 背景

- レポートの**手動 CRUD・承認・Embedding 自動再生成は実装済み**（FR-16 として実装）。
  RAG（FR-10）はこの手動レポートを参照して動いており、**Bot の品質はすでに成立している**。
- 未実装なのは AC-08-01（AI が Slack 履歴から月次レポートを自動生成）と
  AC-08-02（承認後の生徒チャンネルへの Slack 送信 + `slack_message_ts` 保存）。
  `reports.generated_by_ai` は現状 false 固定（BR-08-07 未達）。
- `guardian_email` への保護者メール通知（FR-14）も、送信処理が無いため同じく未実装。
  `RESEND_API_KEY` / `RESEND_FROM_EMAIL` は env スキーマに枠があるだけで参照コードは 0 件。

### 提案

| 項目 | 内容 |
|------|------|
| 起動方式 | **管理画面の「AI 下書きを生成」ボタン + `after()`**。DEC-16 は「月末 Cron で自動生成」としており、DEC-13（即時応答経路限定の Cron 不使用）とは実際には衝突しないが、押した瞬間に `jobs` へ積み `after()` で回す方式なら既存基盤（リトライ・`/admin/jobs` の可視化・スイーパ）にそのまま乗れるため、こちらを採用する |
| 生成単位 | 生徒 1 名ごとに 1 ジョブ。DEC-16 の「3名分割」はジョブ分割で自然に満たせる |
| 入力 | 対象月の `slack_messages` + `ai_usage_logs` + 既存 `student_profiles` |
| 出力 | `reports` に `status='ai_draft'` + `generated_by_ai=true` で保存 → スタッフが編集・承認（`approved`）→ 送信（`sent`） |
| 送信 | 承認後に生徒チャンネルへ `chat.postMessage`、`slack_message_ts` を保存。失敗は `ai_error_logs` に残し `/admin/jobs` から再実行 |
| 保護者メール | Resend で送信（DEC-16）。`RESEND_*` の参照コードをここで初めて書く |
| 承認待ち通知 | `#alerts`（`SLACK_ALERTS_CHANNEL_ID`）へ。kill_switch 通知の実装をそのまま流用できる |

**内訳（概算 8〜12 日）**

- 生成ジョブ（プロンプト設計・月次集計クエリ・`jobs` 種別追加）: 3〜4日
- 管理画面（生成ボタン・一括生成・進捗表示・下書きの差分編集 UI）: 2〜3日
- 承認 → Slack 送信 + `slack_message_ts` + 二重送信ガード: 1〜2日
- 保護者メール（Resend 導入・テンプレート・送信失敗時の扱い）: 1〜2日
- テスト・ドキュメント（FR-08 / FR-14 の status 更新、エラーコード表追記）: 1日

### 先送りしても回る理由

- スタッフが手書きしたレポートでも **RAG の参照データとしては完全に等価**。
  Bot の回答品質は今リリースの範囲で成立している。
- 月次レポートは月 1 回・生徒 50 名の作業。初期は手書きのほうが文面の品質を確かめられる。
- 生成物の品質基準（何を書くべきか）が運用データ無しでは決めきれない。
  **手動で 2〜3 ヶ月書いてから型を抽出したほうが、作り直しが減る**。
- ローンチ前チェックリスト（`docs/03_技術設計/08_ローンチ計画.md` 2.1）に
  「手動レポート運用で開始することを関係者と合意済み」のチェック項目を置いてある。

## 2. FR-05: トピック検出と socratic / confirmation の実働

### 背景

- モード選択（`selectMode`）・3 モードのプロンプト（`buildPrompt`）・BKT 更新式・忘却減衰・
  Evaluator（2 エージェント構成・Zod 構造化出力・低確信度スキップ）は **すべて実装済み**。
- 動いていないのは **質問時のトピック検出**だけ。
  `executeProcessMessage` は `getMastery(db, personId, null)` を呼んでおり、
  topic が null なので常に `P_MASTERY_DEFAULT = 0.2` が返る。
  → `selectMode` は `0.2 < P_MASTERY_DIRECT_MAX(0.3)` で **常に `direct`**。
- その結果 **Evaluator は 1 度も起動しない**。これはバグではなく設計（A-8）:
  `EVALUATOR_MODES = ['socratic','confirmation']` でガードしている。
  direct には確認質問が無いため、「直前に assistant 発言がある」だけで評価すると
  通常の回答を誤って採点して BKT を汚染し、毎ターンの LLM コストも 2〜3 倍になる。
- 試験期間中に direct を選ぶのは DEC-18 準拠（要点重視・スピード優先）で、これは**変えない**。

### 提案

| 項目 | 内容 |
|------|------|
| トピック検出 | 質問文（+ 直近履歴）から `learning_concepts` のトピックを 1 つ特定する。まずは軽量 LLM 1 コール（既存 `LLM_MODEL_DEFAULT`）で `{topic, confidence}` を Zod で受ける。`confidence` 低 → `UNKNOWN_TOPIC` にフォールバックして BKT 更新をスキップ（既存の `LOW_CONFIDENCE_SKIP` と同じ扱い） |
| 反映 | `getMastery(db, personId, detectedTopic)` に差し替えるだけでモード分岐が生きる（既存コードの 1 行） |
| ドロップバック | AC-05-04（socratic で不正解 2 連続 → direct へ降格, BR-05-06）。`student_knowledge_states` の連続不正解カウントを見る |
| 観測 | `ai_usage_logs` にモードを残し、`/admin/usage` でモード別の分布とコストを見られるようにする |

**内訳（概算 6 日）**

- トピック検出（プロンプト・Zod スキーマ・フォールバック・キャッシュ）: 2日
- `getMastery` 連携 + モード分岐の実運用検証（socratic / confirmation の文面調整）: 1.5日
- ドロップバック（AC-05-04）: 1日
- コスト影響の計測・`/admin/usage` へのモード列追加: 0.5日
- テスト・FR-05 / FR-23 の status 更新: 1日

### 先送りしても回る理由

- **direct モードでも「伴走者」プロンプトは効いている**。答えの丸写しを避ける方針は
  モードに依らずシステムプロンプト側で担保している。
- socratic / confirmation を出すには **P(mastery) の推定が信用できる必要がある**。
  トピック検出を入れた初日は全生徒が P=0.2 スタートで、しばらくは結局 direct になる。
  **BKT はデータが貯まるまで判定が当てにならない**ので、先に運用を回して
  `slack_messages` を貯めるほうが順序として正しい。
- コストが読める。Evaluator が動き出すと LLM コールが 1 ターンあたり 2〜3 倍になるため、
  **実利用量が見えてから**入れたい（現在の見積もりは月 ~$5。3 倍でも許容範囲だが実測が欲しい）。
- リスクは「BKT テーブルにデータが溜まらない期間が延びる」ことだけ。
  スキーマ（`student_knowledge_states`）は既に存在しており、後から埋められる。

## 3. 外部 APM（Sentry 等）の導入

### 背景

- **未導入**。`@sentry/*` 依存も `SENTRY_DSN` も存在しない。
- 現在の観測手段:
  1. `ai_error_logs`（`logError()` が全エラーを構造化して記録。severity / 対応状況で絞り込み可）
  2. 管理画面 `/admin/errors`（未対応エラー）・`/admin/jobs`（滞留 KPI）・`/admin/usage`（コスト・エラーコード内訳）
  3. Vercel Logs（`[slack/events]` `[processJob]` `[killSwitch]` `[rateLimit]` `[slack]` のプレフィックス付き `console.warn` / `console.error`）
- 自動アラートは **kill_switch の状態変化のみ**（DEC-15 → `#alerts`）。他は日次の目視確認。

### 提案

| 項目 | 内容 |
|------|------|
| 導入するもの | `@sentry/nextjs`（`SENTRY_DSN` / `SENTRY_AUTH_TOKEN`）。`tracesSampleRate` は 0.1 程度 |
| 送るもの | `logError()` で拾いきれない**想定外の例外**（Server Component / Server Action / `after()` の外側）。`ai_error_logs` に入るものは二重送信しない |
| マスキング | `beforeSend` で `authorization` ヘッダ・Slack token・生徒本文を落とす（`raw_error` の allowlist と同じ方針） |
| アラート | エラーレート > 5件/5分 → `#alerts` |

**概算工数: 1日**（SDK 導入・`beforeSend` のマスキング・Source Maps・アラート設定）

### 先送りしても回る理由

- **エラーの構造化保存はすでにできている**。`ai_error_logs` は Sentry より
  ドメイン情報（person_id / channel_id / thread_ts / error_code / retryable）が濃い。
- 生徒 50 名・月 1,000 質問の規模では **1 日 1 回 `/admin/errors` を見れば十分追える**。
- 「まず何が・どれくらい起きるか」が分かる前に APM を入れると、
  アラート閾値を勘で決めることになり、オオカミ少年化しやすい。
- 判断材料: 運用 1 ヶ月後に `/admin/errors` の severity=error 件数と
  「ログに出ずに Vercel Logs だけで見つかった障害」の件数を数え、後者が 0 でなければ導入する。

| 4-1 | ダッシュボードに jobs 滞留カード | `/admin` の KPI は「今日の質問数 / 今月のコスト / 未対応エラー / 生徒数」の 4 枚。ジョブ滞留は `/admin/jobs` を開かないと分からない | `/admin` に「待機中 / 処理中」の件数カードを 1 枚追加し、0 件でないときだけ強調表示。`/admin/jobs` へのリンクを張る | 0.5日 | 日次で `/admin/jobs` を開く運用を Runbook（06_運用設計 5章 S-04）に明記済み。開けばスイープも自動で走る |

| 4-3 | SCR-03 / SCR-04 の残り表示項目 | AC-14-01 の「最終利用日時・今月の質問数」が一覧に無い（`getPersons` は `persons` 単表 SELECT）。SCR-04 の⑤利用推移グラフ・⑥月次レポート一覧も未実装 | 一覧は `ai_usage_logs` の集計 RPC を 1 本足して JOIN（N+1 にしない）。グラフは既存の recharts + 表フォールバック（`/admin/usage` と同じ書式）を流用 | 1.5日 | スタッフの主目的は「生徒の登録とプロフィール編集」で、利用実績は `/admin/usage` の生徒別内訳で見られる。FR-14 の status は `defined` に戻して未達を明示済み |
| 4-4 | 単価未登録モデルの管理画面警告 | `MODEL_PRICING` に無いモデルは `estimated_cost = 0` で記録される（トークン数は記録される）。プロバイダを切り替えて単価登録を忘れると **コストが $0 のまま積み上がり暴走に気づけない** | `/admin` の「今月のコスト」カードと `/admin/usage` のモデル別内訳で、`findModelPrice()` が undefined を返すモデルに「単価未登録」バッジを出す | 0.5日 | ローンチ前チェックリスト（08_ローンチ計画 2.3）に `MODEL_PRICING` 登録の確認項目を置いた。Runbook（S-03 手順5）にも「コストが不自然に小さいときは `MODEL_PRICING` を疑う」と記載済み |
| 4-5 | `authenticated.spec.ts` サイドバー巡回テストの flake 安定化 | 「サイドバーの全リンクを巡回できる」は 1 テストで 8 画面を順にクリックしていく。1 画面でも遅いと連鎖して落ち、失敗時にどの画面が原因か分かりにくい | 巡回テストを画面ごとに分割するか、各 `click` の後に `waitForURL` を明示。直接 URL を開く 8 テストは既にあるので、巡回テストは「リンクの `href` 検証」に絞るのも手 | 0.5日 | 2026-08-02 時点で E2E 56件は全 pass。flake は再現していないため、落ちてから直しても損失が小さい |
