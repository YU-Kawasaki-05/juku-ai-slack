## A. 実行基盤・ジョブ（コア処理系）

### A-1 ★★★ maxDuration 未設定 + ジョブ孤児の回収機構なし
- `src/app/api/slack/events/route.ts`（`export const maxDuration` がリポジトリに1つもない）
- `after()` 内の処理が Vercel 既定タイムアウトで kill されると、jobs は processing のまま、🤔 残存、エラーログなし、生徒に無応答。
- 対処: `maxDuration = 300` + 滞留ジョブのスイーパ（processing/pending が閾値超過→failed 化+JOB_TIMEOUT 記録）+ 管理画面 jobs 可視化。

### A-2 ★★★ after() 内 claim 失敗で完全無音消失
- `route.ts:227` × `processJob.ts:83`。claim の throw は誰にも観測されず、receipt が残るため Slack 再送も duplicate 扱いで二度と処理されない。
- 対処: after コールバックを try/catch で包み logError + 可能なら Slack 通知。`slack_event_receipts.status/processed_at`（型はあるが書き込みコードゼロ）を実際に更新し再処理可能に。

### A-3 ★★★ リトライ圏内に postMessage + LLM 課金が同居（二重返信・二重課金）
- `processJob.ts:110-134` × `executeProcessMessage.ts:138-155`。投稿成功後の応答タイムアウトで throw → リトライで同内容2通 + LLM 再課金。失敗 attempt の usage は未記録（コスト過少計上）。
- 対処: 生成（リトライ可）と配信（1回限り）を分離。生成結果を jobs 行に保存してから投稿、リトライ時は再生成しない。SlackPostFailedError は非リトライアブル化。失敗 attempt も logUsage。

### A-4 ★★ user メッセージ保存が返信後（並行時の文脈欠落・順序逆転）
- `executeProcessMessage.ts:151-185`。質問の INSERT が回答投稿の後。LLM 待ちの間に追撃が来ると後続ジョブが文脈ゼロで回答。postMessage 3連続失敗時は履歴に恒久的な穴。
- 対処: saveMessage(user) を generateAnswer の前へ。`slack_messages` に UNIQUE(channel, thread_ts, message_ts, role) を追加し upsert 化。

### A-5 ★★ 即時スレッド返信の取りこぼし（セッション作成がジョブ内）
- `route.ts:129-131` × `executeProcessMessage.ts:37-44`。メンション直後〜claim 完了の窓に来たスレッド返信が unregistered_thread 扱いで無言破棄。
- 対処: decision=process 確定後、enqueue 前に受信ハンドラ側で getOrCreateSession を実行。

### A-6 ★★ 要約の二重実行（CAS なし）
- `summarizeThread.ts:121-127`。並行ジョブが同一計画で要約 LLM を2回呼び、後勝ちで片方のコストが捨てられる。
- 対処: UPDATE に `.eq('summary_message_count', summarizedCount)` を付け CAS 化。0行更新なら破棄。

### A-7 ★★ ACK パスの直列 DB 4往復（3秒予算超過リスク）
- `route.ts:87-131,224`。receipt→lookupBinding→findSession→enqueueJob が直列。コールドスタート+遠隔 Supabase で3秒超過→Slack 再送増加。
- 対処: lookupBinding と findSession を Promise.all 化（最低限）。

### A-8 ★★ Evaluator が毎ターン無駄に走り BKT 汚染 + コスト2-3倍
- `executeProcessMessage.ts:203,287-345`。direct モード（現状全て）では確認質問が無いのに、直前 assistant 発言があるだけで評価が走る。
- 対処: Evaluator の起動を「直前の Bot 発言が確認質問を含むターン」に限定（modeが socratic/confirmation のとき、または応答フラグ）。

### A-9 ★★ BKT の read-modify-write 競合 + botQuestion の取り違え
- `applyEvaluation.ts:64-98`。並行更新で attempt_count が lost update。並行時は無関係な問いに対する評価が書かれる。
- 対処: BKT 更新を RPC（単文 UPDATE + UPSERT）化。botQuestion は当該 message_ts の直前 assistant 行を明示的に引く。

### A-10 ★★ リトライ二重ネスト（最大9回 LLM 呼び出し・最長540秒）
- `openaiCompatibleClient.ts:51-55`（SDK 既定 maxRetries=2）× `processJob.ts`（3 attempts）。
- 対処: `maxRetries: 0` を明示（ジョブ側リトライに一本化）。

### A-11 ★★ 429 バックオフ短すぎ / 非リトライアブルもリトライ
- `processJob.ts:119`（500ms/1000ms）。429 は1.5秒で使い切り。TOKEN_BUDGET_EXCEEDED 等の恒久エラーも3回リトライ。
- 対処: AppError に retryable フラグ。非リトライアブルは即 failed。429 は長めのバックオフ。

### A-12 ★★ 要約連続失敗時に履歴窓が古い側へ固定
- `executeProcessMessage.ts:116-125` × `threadHistory.ts:86-87`。未要約が30件超で直近のやり取りが履歴から落ちる。
- 対処: tail 上限超過時は新しい方から30件（降順取得→反転）。

### A-13 ★ created_at 単独ソートでタイブレーカなし [要検証→修正が安い]
- `threadHistory.ts:29,84`。同時刻 INSERT でページ境界の取りこぼし/重複の可能性。
- 対処: `ORDER BY created_at, id` に変更。

### A-14 ★ receipts/jobs の掃除ジョブなし
- 運用設計は receipts 30日 / jobs 7日削除前提。実装なし。
- 対処: pg_cron（Supabase 標準）で定期 DELETE、不可なら opportunistic 削除。

### A-15 ★ finish_reason 未検査（length 打ち切りを正常投稿 / Evaluator 恒常失敗）
- `openaiCompatibleClient.ts:70-82`。Evaluator は CoT スキーマ + 500 tokens で恒常的に切れ、AI_RESPONSE_FAILED に化けて課金だけ発生。
- 対処: finish_reason==='length' を検出。EVALUATOR_MAX_TOKENS 増枠 or リトライ時増枠。

## B. RAG / Embedding パイプライン

### B-1 ★★★ encoding_format 未指定 → 非対応プロバイダでベクトルが静かに壊れる（実測済み）
- `embeddingClient.ts:27`。openai SDK v6 は未指定だと base64 を要求し無条件デコード。float 配列を返すプロバイダでは全ゼロ 384 次元に化ける。
- 対処: `encoding_format: 'float'` を明示。

### B-2 ★★★ ベクトル数不足時に NULL embedding が無言 INSERT
- `rebuildReportEmbeddings.ts:46`。`JSON.stringify(undefined)` でキー消失→ DEFAULT NULL。RPC は IS NOT NULL で除外→永久に検索対象外。成功扱い。
- 対処: `vectors.length !== chunks.length` で throw。embed 側でも件数検査。

### B-3 ★★ res.data を index ソートせず（ベクトル入れ違い）
- `embeddingClient.ts:28`。順序保証のないプロバイダで本文とベクトルが入れ違い保存 → RAG が静かに嘘をつく。
- 対処: `sort((a,b)=>a.index-b.index)`。

### B-4 ★★ 次元検証ゼロ + 検索エラー握りつぶしで RAG 無言全滅
- `searchChunks.ts:34-44`、`EMBEDDING_DIM=1536` は宣言のみ未参照。
- 対処: embed 戻りで次元検証。設定ミスを即時エラー化。

### B-5 ★★ ivfflat を空テーブルに構築（低リコール）
- `005_create_report_chunks.sql:14-15`。lists=100 を空テーブルで作成 → probes=1 では大半が探索対象外。
- 対処: 小規模データではインデックス DROP（seq scan で十分）。閾値 0.7 も実データで再確認。

### B-6 ★★ rebuildReportEmbeddings が非トランザクション・無ロック・UNIQUE なし（並行で重複/陳腐化）
- `rebuildReportEmbeddings.ts:33-50`。自動再生成と手動ボタンの並行で v1/v2 チャンク混在。read-then-write で旧本文が固定されるケースも。
- 対処: UNIQUE(report_id, chunk_index) 追加 + RPC 化（DELETE+INSERT を1トランザクション）+ advisory lock。

### B-7 ★★ 画像のみメッセージで空文字を Embedding API に投げる
- `executeProcessMessage.ts:135` → `searchChunks.ts:34`。OpenAI は '' を 400 拒否 → 質問ごとに無駄呼び出し+エラーログ。
- 対処: searchChunks 冒頭で `if (!queryText.trim()) return []`。

### B-8 ★★ EMBEDDING 未設定時のログ洪水
- `executeProcessMessage.ts:272-281`。全メッセージで REPORT_CHUNK_SEARCH_FAILED(warning) が積まれる。
- 対処: 設定未了は起動時判定でスキップ（毎回ログしない）。Evaluator 失敗は EVALUATOR_FAILED に分離。

### C-7 ★ [要検証→1行修正] mimetype を Slack 申告値のまま使用
- `processAttachments.ts:91`。downloaded.contentType を SUPPORTED_IMAGE_MIMETYPES で再検証して採用。
