### 実測でわかったこと（ローカル Supabase v2.190.0）

- `generate_link(type=recovery)` の `action_link` を開くと Supabase は 303 を返し、
  **成功も失敗もフラグメント**に載る。
  成功 `#access_token=...&refresh_token=...&type=recovery` /
  失敗 `#error=access_denied&error_code=otp_expired&...`。
  サーバーからは読めないので Client Component が必須。
- リンクは **1 回限り**。2 回目は期限切れ（`otp_expired`）と同じ応答になる。
  期限切れ・使用済み・不正トークンを区別する情報は返らない。
- 有効期限は `GOTRUE_MAILER_OTP_EXP`（= `config.toml` の `[auth.email] otp_expiry`）で
  **既定 3600 秒 = 1 時間**。コンテナの env で確認済み。
- `redirect_to` は **ループバック IP なら任意のポート・パスが通る**が、
  ホスト名 `localhost` は通らず**黙って Site URL に差し替えられる**（エラーにならない）。
  本番はダッシュボードの Redirect URLs に `/set-password` を登録すること。
- パスワード変更（`PUT /auth/v1/user`）は Bearer トークン必須。
  トークンなし → 401 `no_authorization` / anon キー → 403 `bad_jwt`。
  つまり画面が未認証で開けても他人のパスワードは変えられない。

### middleware

**変更なし**（matcher は `['/admin/:path*', '/login']` のまま）。
`/set-password` を matcher に入れると未認証アクセスが `/login` にリダイレクトされ、
その際に URL フラグメントが失われて招待リンクが機能しなくなる。
この事故を防ぐためコメントを追記し、`e2e/auth-guard.spec.ts` に
「`/set-password` は未認証で開ける」テストを追加して固定した。

### 最低文字数

FR-13 は 8 文字以上、Supabase の既定は 6。UI 側が緩いと「入力は通ったのに保存で 422」に
なるため、`supabase/config.toml` の `minimum_password_length` を 8 に上げて UI と揃えた。
本番は Authentication → Sign In / Providers → Email の Minimum password length も 8 にする
（手順書に記載）。
