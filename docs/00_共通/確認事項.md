### §2-0. 【新規・GitHub の設定画面】ブランチ保護を有効にする

**なぜ必要か**: CI を「PR で E2E smoke を走らせる」構成に変更しましたが、**ブランチ保護が未設定のため、テストが赤でもマージできます**。`gh api` で確認したところ `404 Branch not protected`、ruleset も空でした。テスト戦略ドキュメントの「Block merge」は現状ただの文言です。

**操作手順**
1. GitHub のリポジトリ → **Settings** → **Branches** → **Add branch protection rule**
2. Branch name pattern に `main` を入力

4. 検索欄で以下3つを追加（**一度 PR を作って CI を走らせないと候補に出てきません**。先に §2-6 の PR を作ってから設定するとスムーズです）

   - `Unit Tests`
   - `E2E Smoke`
5. 保存後、同じ手順で `develop` にもルールを追加

**補足**: これは workflow ファイルからは設定できない GitHub 側の設定です。所要 5 分程度。

### §2-4. Vercel デプロイと環境変数

**ご質問への回答: 「環境変数を設定する」とは何か / デプロイ前か後か**

Vercel の **Project Settings → Environment Variables**（またはインポート画面）で値を登録する作業です。

**デプロイ前に設定が必要です。** 実際に環境変数を空にして `next build` を走らせて検証した結果:

- **必須6個のうち1つでも欠けると、ビルド自体が失敗**します（実行時 500 ではなく、Vercel のビルドが `Collecting page data` で落ちる）。`src/shared/lib/env.ts` がモジュール読み込み時に検証して throw するためです
- さらに **Supabase に実際に疎通できないとビルドが失敗**します（`/admin` の静的化を試みる際に本物のクエリを1回投げるため）。だから §2-2・§2-3 を先に終わらせる必要があります
- 逆に **AI 回答用4個・RAG 用3個・任意3個はビルドをブロックしません**（実行時にしか使われない）。ただし追加・変更したら**再デプロイが必要**です（Vercel は環境変数をデプロイ単位で固定するため）

**必要な環境変数がまとまっているファイル（全19個で一致を確認済み）**

| ファイル | 役割 |
|---|---|
| `src/shared/lib/env.ts` | **実装の正**（Zod スキーマ。必須/任意の最終根拠） |
| `docs/06_セットアップガイド/step5_vercelデプロイ.html` §5-2 | 変数の一覧表＋取得元＋注意点 |
| `docs/05_その他/2026-08-02_本番移行_決定事項と制約.md` §7 | **この案件で入れる実際の値** ← モデル名などはこちらが正 |
| `.env.example` | ローカル開発用のひな形 |

⚠️ **ガイドの例（`gpt-4o-mini` など）ではなく、決定事項ドキュメント §7 の値を使ってください。** ガイドは汎用手順なのでプレースホルダになっています。

**必須6個（ビルド前に必要）**

| 変数 | 取得元 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Settings → API → Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 同上 → anon/public |
| `SUPABASE_SERVICE_ROLE_KEY` | 同上 → service_role（**`NEXT_PUBLIC_` を絶対に付けない**） |
| `SLACK_BOT_TOKEN` | Slack アプリのインストール後に表示（`xoxb-`） |
| `SLACK_SIGNING_SECRET` | Slack アプリ → Basic Information |
| `SLACK_BOT_USER_ID` | `auth.test` の `user_id`（**`U` 始まり**。`B` 始まりの Bot ID を入れると永久に無反応） |

**設定してはいけない / 意味がない変数**
- `ANTHROPIC_API_KEY` — SDK を依存から外したので使われません
- `RESEND_API_KEY` / `RESEND_FROM_EMAIL` — 参照コードがゼロ。**行ごと作らない**（空文字で作るとメール形式検証に失敗し、Slack 連携を含むアプリ全体が 500 になります）

**操作手順**: `docs/06_セットアップガイド/step5_vercelデプロイ.html`

2. Sensitive 指定の付け方もガイドに手順がありません（`SUPABASE_SERVICE_ROLE_KEY` などは Sensitive 推奨）

### §2-5. Slack アプリの作成とアラート用チャンネル

**操作手順**
- アプリ作成: `docs/06_セットアップガイド/step4_slackアプリ作成.html`
- イベント購読: `docs/06_セットアップガイド/step6_slackイベント購読.html`

**手順の全体像**（読む前に把握しておくと迷いません）

1. api.slack.com/apps で **manifest を貼り付けて作成**（step4 に manifest 全文があります。From scratch の手順も併記）
2. Bot Token Scopes は**5つだけ**: `chat:write` / `reactions:write` / `channels:history` / `groups:history` / `files:read`
   - 非公開チャンネル運用なので `groups:history` が必須。公開用の `channels:history` も入れておくと後で公開チャンネルを追加するときに再インストールが不要
3. ワークスペースにインストール → **`xoxb-` トークンを控える**
4. Basic Information → **Signing Secret を控える**
5. `auth.test` を叩いて **Bot User ID（`U` 始まり）を控える**
6. **ここでいったん止める**（Event Subscriptions は設定しない）
   - 理由: Request URL の登録時に Slack が検証リクエストを送りますが、**署名検証を通すには `SLACK_SIGNING_SECRET` が設定済みのデプロイが必要**です。デプロイ前に登録すると必ず失敗します
7. §2-4 のデプロイ完了後に step6 へ進み、Request URL に `https://<ドメイン>/api/slack/events` を登録して **Verified** を確認
8. Subscribe to bot events に `message.channels` と `message.groups` を追加（**`app_mention` は不要**。メンション検出は本文の文字列一致で行っています）

**アラート用チャンネル（`SLACK_ALERTS_CHANNEL_ID`）**
- 用途: AI の緊急停止スイッチ（kill_switch）を停止/再開したときの通知先
- 値: チャンネル ID（`C` 始まり）。Slack でチャンネルを開き「チャンネル詳細」の最下部に表示される ID、または URL の末尾
- **Bot をそのチャンネルに招待する必要があります**（`/invite @<Bot名>`）。スコープに `chat:write.public` を含めていないため、招待しないと投稿できません
- 未設定でも停止/再開の操作自体は成功します（通知だけ飛びません）

**権限について**: 決定事項では「通常メンバーで足りる見込み」としています。step4 のインストールボタンが `Install to <ワークスペース>` と表示されれば確定、`Request to Install` なら管理者の承認依頼が必要です。

### §3-3. Vision モデル未設定について（ご質問6への回答）

**何のための設定か**: `LLM_MODEL_COMPLEX` は「**画像が添付された質問のときだけ使うモデル**」です。テキストのみの質問は `LLM_MODEL_DEFAULT` を使います。両者は API キーと base URL を共有するため、**同じプロバイダのモデルでなければなりません**（これが OpenAI 直に統一した理由）。

**どういう場合に未設定になるか**（実質、初回セットアップの設定漏れがほぼ唯一の経路）
1. Vercel で環境変数の行を作り忘れる
2. Preview 環境にだけ設定して Production に入れ忘れる（Vercel は環境ごとに別管理）
3. 変数名のタイポ
4. 値を空文字で登録する

**通常運用で勝手に外れることはあるか**: ありません。一度正しく設定すれば、誰かが Vercel の設定を触るまで維持されます。

**発生頻度の想定**: 初回セットアップ時のみ。運用中に発生する経路はほぼありません。

**ではなぜ対応したのか**: 実装コストが小さく（既に完了）、かつ**未対応時の症状が「画像付き質問の回答自体が失敗する」という分かりにくいもの**だったためです。現在は「画像だけ読まれず、テキストで回答が返り、生徒に理由が伝わる」挙動になっており、万一の設定漏れでも Bot が使えなくなりません。

⚠️ **より重要な別のリスク**: コードは「環境変数が設定されているか」しか見ておらず、**設定されたモデルが本当に Vision 対応かは判定していません**。つまり `LLM_MODEL_COMPLEX` に Vision 非対応のモデル名を入れると、今回の保険は効かず**回答が失敗します**。§2-1 の実測で `gpt-5.6-terra` が画像を処理できることを必ず確認してください。

**ユーザー側で必要な作業**: §2-4 で `LLM_MODEL_COMPLEX` に §2-1 で確定したモデル ID を設定するだけです。

### §4-4. EXIF（メタデータ）除去の実装 — 独立検査 PASS

**画質を一切落とさない方法を選びました。** 画像処理ライブラリ（sharp）を使うと、どの経路を通っても必ずデコード→再エンコードが走り、JPEG では非可逆になって画質が落ちます。そのため **sharp は使わず、バイト列レベルでメタデータ領域だけを削除**する実装にしました（ピクセルデータの領域には一切触れません）。

| 形式 | 削除するもの | 意図的に残すもの |
|---|---|---|
| JPEG | EXIF・GPS・XMP・IPTC・コメント | JFIF、**ICC プロファイル**、Adobe マーカー（落とすと色再現が変わる＝画質に影響するため） |
| PNG | テキストチャンク・EXIF・タイムスタンプ | 画像本体、色空間情報 |
| WebP | EXIF・XMP | 画像本体、色空間情報 |

解析に失敗した場合・未知の形式の場合は**元のデータをそのまま返す**フェイルセーフにしています（画像が壊れて質問に答えられなくなる方が害が大きいため）。

**削減効果の実測**: 実カメラ相当の 30KB の EXIF を含む画像で **-30,004 バイト**、かつ EXIF を入れる前の原本とバイト単位で完全一致。

**独立検査の結果（別エージェントが実装者の報告を疑って再検証）**
- ピクセル不変: progressive JPEG・CMYK・16bit PNG・実アニメーション WebP など実装者が試していない条件でも、デコード後のピクセルのハッシュが一致
- GPS 除去: 自作バイナリで GPS 座標・MakerNote・埋め込みサムネイルを仕込んだ画像で、**1バイトも残らない**ことを確認
- 壊れた入力 7,020 ケース・ビット反転 9,000 ケース: 例外 0 件・画像破損 0 件
- ミューテーションテスト: 実装を4通り壊すと、対応するテストが全て落ちた（テストが空洞でないことの確認）
- 判定: **PASS。発見された問題なし**

**副次的なメリット**: EXIF の GPS 情報が消えるため、生徒の自宅位置などが LLM やストレージに残らなくなります。

### §4-5. CI の E2E 方針の実装

| ジョブ | トリガ | 内容 |
|---|---|---|
| Lint & Type Check / Unit Tests | 常時 | 型チェック・Lint・ユニット 792 件 |
| **E2E Smoke**（新規） | PR | 3 spec / 20 テスト（権限境界・Slack フロー・コスト制御） |
| E2E Fullsuite | main への push | 86 件（従来どおり） |

**実装中に見つかった設計上の穴**
1. **`on.pull_request.branches` が `[main]` だけだった** — 実際の運用は feature → develop → main なので、**feature → develop の PR には E2E が一切走らない**状態でした。`develop` を追加して修正
2. **Playwright は存在しない spec パスを黙って無視して成功扱いにする**（`exit 0`）。ファイル名を変えたときに smoke が静かに縮むため、パス存在チェックを追加
3. **ブランチ保護が未設定** → §2-0（ユーザー操作）

**実行時間の見積もり**（CI 実測ではなく積み上げ）: PR の smoke が約7〜9分、main の全件が約9〜11分。公開リポジトリなので費用は ¥0。

**main への反映**: `main` の `ci.yml` は分岐点以降一度も変更されていないことを blob SHA で確認済み。`develop` → `main` のマージでコンフリクトなく置き換わります。

### §4-6. バックアップとリストア — 既存手順書に重大な誤りがありました

**発見1: 既存手順のコマンドでは生徒データが1行も取れていませんでした。**
`docs/06_セットアップガイド/step9_運用ガイド.html` が案内していた `supabase db dump -f backup.sql --linked` は、**既定でスキーマ（テーブルの構造）のみを出力し、中身のデータを含みません**。この手順に従っていたら「バックアップを取っているつもりで、実際には空だった」という最悪のケースになっていました。修正済みです。

**発見2: リストアが丸ごと失敗する条件があります。**
Supabase 内部のテーブルで権限エラーが出ると、トランザクションが巻き戻って**データが1行も入りません**。実際に最初のリストア試行がこれで失敗しました。除外設定を既定に入れて解決済みです。

**実施したリストア訓練（ロードマップの完了条件「取れているだけでは不十分。1回リストアを試すこと」を満たすため）**

検証用に別の Supabase を立てて（既存のローカル環境には触らず）、次を実施しました。

1. 代表データを投入（日本語・改行・引用符を含む文章、1536次元のベクトル、自己参照する外部キー、認証ユーザー）
2. バックアップを取得
3. **`db reset` で全損をシミュレート**
4. バックアップから復元
5. 検証SQL で照合 → **17テーブルの行数・本文のハッシュ・ベクトルの次元と内積・RLS ポリシー・インデックス・権限すべて一致**
