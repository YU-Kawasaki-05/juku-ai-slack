# セットアップ手順（管理画面の運用前に必要な設定）

> **位置づけ**: 新規セットアップ（顧客先での 0 からの構築）の正本は
> **`docs/06_セットアップガイド/index.html`** です。
> 本書はそのうち **「管理画面を運用に乗せる前に必要な設定」の詳細** を扱います。
> 手順が食い違う場合は、実装（`src/shared/lib/env.ts` / `supabase/migrations/`）→ HTML ガイド → 本書の順に信頼してください。

管理画面の一部機能は、コードではなく **環境側の設定** が必要です。ここに集約します。
コピペで実行できる粒度で書いています。対象読者はプロジェクトオーナー／運用担当。

> 設定が不要な機能（生徒管理・チャンネル紐付け・レポートの手動作成・エラー管理・
> 利用状況・会話ログ）は、ログインすればそのまま使えます。下記は「特定機能を有効化する」設定です。

## 前提

- Supabase プロジェクトが作成済み
- migration（`supabase/migrations/001`〜`032`）が適用済み
- リポジトリ直下に `.env.local` がある（無ければ `cp .env.example .env.local` して実値を記入）
- 管理画面にログインするユーザーが Supabase Auth に登録済み
  （Supabase ダッシュボード → Authentication → Users → **Add user** で個別に招待する。
  セルフサインアップは手順0で塞ぐので、ここ以外から増やせないようにする）

---

## 手順0: サインアップの無効化 【必須・セキュリティ】

### なぜ必要か

migration `026_harden_rls_policies.sql` で RLS を
「`app_metadata.role` が `staff` / `admin` のユーザーの **SELECT のみ**」に絞り、
authenticated の INSERT / UPDATE / DELETE は全て剥奪しています。

ただし **これは「誰でもサインアップできない」ことが前提** です。
サインアップが開いたままだと、第三者が自分でアカウントを作って
anon key + 自分の JWT で PostgREST に到達できてしまいます
（role が無ければ SELECT も通りませんが、認証境界を外部に開ける理由がありません）。
026 のヘッダにも「これをやらないと本 migration の効果が薄れる」と明記しています。

### 手順

1. Supabase ダッシュボード → **Authentication** → **Sign In / Providers**
2. **「Allow new users to sign up」を OFF** にする
3. 管理画面ユーザーは Admin API / ダッシュボードから **個別に招待**する（招待制）
4. 招待した全ユーザーに `app_metadata.role`（`staff` または `admin`）を必ず付与する（手順1）

> `user_metadata` はログイン中の本人が書き換えられるため、権限判定には使いません。
> `app_metadata` は Service Role / Admin API でしか書けないので自己昇格できません。

### 確認

```sql
-- role が未設定のユーザーが残っていないか（該当行が 0 件なら OK）
select email, raw_app_meta_data
from auth.users
where coalesce(raw_app_meta_data ->> 'role', '') not in ('staff', 'admin');
```

## 手順1: 管理者・スタッフロールの付与 【必須】

### なぜ必要か

`app_metadata.role` は 2 つの役割を持ちます。

1. **管理者だけができる操作の判定**（`requireAdmin`）:
   レポートの **Embedding 手動再生成**（EP-14 / BR-16-02）、
   **AI 応答の停止・再開**（DEC-15 の KillSwitchCard）
   — どちらも全生徒に影響する / コストが発生する操作です。
   **チャンネル紐付けの作成・更新（EP-07〜09）は staff でも可**（担当スタッフが行う運用。
   `docs/02_外部設計/03_権限設計.md` 3.1）
2. **RLS の通過判定**（migration 026 の `is_staff_or_admin()`）:
   role が無いユーザーは Supabase Studio / REST でテーブルを SELECT できません

`user_metadata` はログイン中の本人が書き換えられて**権限昇格の穴**になるため使いません
（詳細: `docs/02_外部設計/03_権限設計.md`）。

### 方法A: Supabase SQL Editor（最短・おすすめ）

Supabase ダッシュボード → SQL Editor で以下を実行（メールアドレスは対象ユーザーのもの）:

```sql
-- 管理者
update auth.users
set raw_app_meta_data = raw_app_meta_data || '{"role":"admin"}'::jsonb
where email = 'owner@example.com';

-- スタッフ（管理者以外の運用担当）
update auth.users
set raw_app_meta_data = raw_app_meta_data || '{"role":"staff"}'::jsonb
where email = 'staff@example.com';
```

### 方法B: Admin API（スクリプトで一括付与したい場合）

Service Role キーを使うサーバー専用スクリプトから:

```ts
import { createClient } from '@supabase/supabase-js'
const admin = createClient(process.env.NEXT_PUBLIC_SUPABASE_URL!, process.env.SUPABASE_SERVICE_ROLE_KEY!)
await admin.auth.admin.updateUserById(userId, { app_metadata: { role: 'admin' } })
```

### 反映と確認

1. 付与後、対象ユーザーは **一度ログアウト → 再ログイン**（JWT 再発行で反映される）
2. レポート詳細ページで「Embedding 再生成」ボタン → 確認ダイアログ → 実行できれば OK

### うまくいかないとき

- 「Embedding 再生成は管理者のみ実行できます」と出る → role が未反映。再ログインを確認し、
  次の SQL で `raw_app_meta_data` に `"role":"admin"` が入っているか確認:
  ```sql
  select email, raw_app_meta_data from auth.users where email = 'owner@example.com';
  ```

## 手順2: Embedding の環境変数 【RAG を使うなら推奨】

### なぜ必要か

レポートを保存すると、本文を Embedding（ベクトル）化して Bot 回答の参照データにします（DEC-14）。
この API 接続情報が未設定だと、Embedding 生成だけが失敗します
（**レポートの保存自体は成功**し、詳細ページに「Embedding 再生成が必要です」の警告が出ます）。

### 設定（`.env.local` に追記）

```
EMBEDDING_API_KEY=sk-...
EMBEDDING_BASE_URL=https://api.openai.com/v1
EMBEDDING_MODEL=text-embedding-3-small
```

- OpenAI 互換 API ならプロバイダは差し替え可能（`EMBEDDING_BASE_URL` を変える）
- **設定変更後は dev サーバー／デプロイを再起動**（env は起動時に読まれる）

### 確認

- レポートを保存 → 詳細ページに警告バナーが出ない／「最終 Embedding」日時が更新される
- 既存レポートは詳細ページの「Embedding 再生成」で手動更新できる（手順1の admin 権限が必要）

## 手順3: Slack ワークスペース URL 【任意】

### なぜ必要か

エラー詳細ページの「Slack で開く」リンク（該当スレッドへ直接ジャンプ）に使います。
未設定でも動作しますが、リンクは出ず ID 表示にフォールバックします。

### 設定（`.env.local` に追記）

```
SLACK_WORKSPACE_URL=https://your-workspace.slack.com
```

（再起動後）エラー詳細ページで「Slack で開く」リンクが表示されれば OK。

## 手順4: 運用アラートの通知先チャンネル 【任意・推奨】

### なぜ必要か

AI 応答を停止／再開したとき（DEC-15）、その事実を Slack に自動通知します。
**状態が変化したときだけ**投稿されるので通知は増えません。
未設定でも停止・再開そのものは行えますが、通知はスキップされ `console.warn` が出るだけになります
（「止めたまま忘れる」事故に気づけなくなる）。

### 設定（`.env.local` / Vercel の環境変数に追記）

```
SLACK_ALERTS_CHANNEL_ID=C0XXXXXXXX
```

- 値は**チャンネル ID**（`C` から始まる）。チャンネル名ではありません
- **Bot を対象チャンネルに `/invite` しておくこと**（招待していないと投稿できない）

### 確認

`/admin` の KillSwitchCard で停止 → 再開し、指定チャンネルに
「見出し / 操作者 / 理由 / 時刻（JST）」の 4 行が投稿されれば OK。

## 手順5: DB 型定義の再生成 【migration を追加・変更したとき】

migration を適用したら、TypeScript の DB 型（`src/shared/types/database.types.ts`）を再生成します。
生成しないと新しいテーブル・列がコンパイルエラーになります。

```bash
pnpm supabase:types           # ローカル Supabase を見て生成
pnpm supabase:types:linked    # supabase link 済みのクラウドプロジェクトを見て生成
```

- クラウドに `supabase db push` した後は **`pnpm supabase:types:linked`** を使う
- 生成結果は差分をコミットする（生成物もリポジトリ管理下）

## 補足: 権限の現在仕様

| ガード | 判定 | 使う場所 |
|--------|------|---------|
| `requireStaff` | `app_metadata.role` が `staff` または `admin` | 大半の管理画面 Server Action |
| `requireAdmin` | `app_metadata.role === 'admin'` | Embedding 手動再生成（EP-14）／AI 応答の停止・再開（DEC-15） |

チャンネル紐付けの作成・更新（EP-07〜09）は `requireStaff` 側です。誤操作は
確認ダイアログと操作ログ（`CHANNEL_BINDING_CREATED` / `CHANNEL_BINDING_UPDATED`）で抑えます。

RLS 側（migration 026）は `staff` / `admin` のどちらでも SELECT のみ許可。
書き込みはアプリの Service Role 経由に一本化しています。
ロール未設定のアカウントはログインはできますが管理画面は開けず、`/admin/no-access`
（付与手順とログアウト導線を出す画面）に案内されます。
詳細は `docs/02_外部設計/03_権限設計.md`。
