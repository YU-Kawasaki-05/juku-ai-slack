# 運用設計 — juku-ai-slack-bot

> 本書は実装を正本として記述している。外部 APM（Sentry 等）は**導入していない**。
> 観測は `ai_error_logs` + 管理画面（`/admin/errors` / `/admin/jobs` / `/admin/usage`）+ Vercel Logs で行う。

## 1. ログ設計

### 1.1 出力先

| ログ種別 | 出力先 | 保管期間 |
|---------|--------|---------|
| アプリケーションログ | Vercel Logs（`console.warn` / `console.error` の標準出力） | 1日（Hobby）/ 30日（Pro） |
| エラーログ | `ai_error_logs` テーブル（管理画面 `/admin/errors`） | 無期限（手動削除なし） |
| AI利用ログ | `ai_usage_logs` テーブル（管理画面 `/admin/usage`） | 無期限 |
| Slackイベント受信ログ | `slack_event_receipts` テーブル | 30日で削除（`cleanupOldRows`。6章参照） |
| ジョブ実行ログ | `jobs` テーブル（管理画面 `/admin/jobs`） | 7日で削除（completed / skipped / failed のみ） |

### 1.2 ログレベル方針

| レベル | 用途 | 実装上の出力先 |
|--------|------|--------------|
| ERROR | 復旧不可・即対応が必要 | `logError(severity: 'error')` → `ai_error_logs`。加えて `console.error` |
| WARN | 復旧可能・要確認 | `logError(severity: 'warning')` → `ai_error_logs`。fail-open 系は `console.warn` のみ |
| INFO | 主要イベント・サイレント終了 | `logError(severity: 'info')`（`AI_PAUSED` / `RATE_LIMITED` / `PERSON_INACTIVE` / `LOW_CONFIDENCE_SKIP` など） |
| DEBUG | 開発時のみ | 実装なし（`console.log` は本番コードに置かない） |

### 1.3 構造化ログ

**構造化ログのユーティリティは実装していない**（`src/lib/logger.ts` は存在しない）。
「後から検索したいもの」は `ai_error_logs` に構造化して入れ、標準出力は補助という役割分担にしている。

`logError()`（`src/features/error-logs/lib/logError.ts`）が `ai_error_logs` に書く構造:

```typescript
{
  error_code: string          // 'AI_RATE_LIMITED' など（FR-11 / 02_外部設計/07 の一覧）
  severity: 'error' | 'warning' | 'info'
  internal_message: string    // 内部向けの状況説明
  user_facing_message: string | null
  person_id: string | null
  slack_channel_id: string | null
  thread_ts: string | null
  message_ts: string | null
  retryable: boolean
  raw_error: jsonb | null     // Error は {name,message}、オブジェクトは name/message/code/status のみ許可
}
```

- `raw_error` は allowlist でサニタイズしてから保存する（トークン・PII の混入防止）
- `logError` 自体の失敗は握りつぶして `console.error('[logError] failed to persist error log:', …)` に落とす（ログ保存の失敗で本処理を落とさない）
- 標準出力側は `[slack/events]` `[processJob]` `[killSwitch]` `[rateLimit]` `[slack]` などのプレフィックス付き `console.warn` / `console.error`。Vercel Logs で prefix 検索する運用

### 1.4 個人情報マスキング方針

- `person_id`（UUID）: ログに出してよい（直接個人を特定しない）
- 生徒の氏名: ログに出さない
- Slackメッセージ本文: ログに出さない（`internal_message` には概要のみ）
- APIキー・Token: 絶対にログに出さない

### 3.2 自動停止の仕組み（kill_switch）— 実装済み

DEC-15 のとおり実装済み。**環境変数 `ENABLE_AI` は存在しない**。停止・再開は DB + 管理画面で行う。

```sql
-- supabase/migrations/031_create_kill_switches.sql
CREATE TABLE kill_switches (
  name       TEXT NOT NULL PRIMARY KEY,
  enabled    BOOLEAN NOT NULL DEFAULT true,
  reason     TEXT,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_by TEXT
);

INSERT INTO kill_switches (name, enabled, reason)
VALUES ('ai_responses', true, NULL)
ON CONFLICT (name) DO NOTHING;
```

| 観点 | 実装 |
|------|------|
| チェック関数 | `isAIEnabled(db)` — `src/features/kill-switch/lib/killSwitch.ts` |
| 評価タイミング | `processJob` 冒頭（pending→processing の claim 後、🤔 付与と LLM 呼び出しの**前**） |
| 読み取り失敗時 | **fail-open**（`enabled: true` として続行）。`console.warn` のみ。障害で AI を巻き込み停止させない |
| 停止中の生徒への挙動 | 🤔 を付けない。`AI_PAUSED` の定型文だけ投稿。ジョブは `completed`（`error_code='AI_PAUSED'`）でリトライしない |
| 管理 UI | `/admin` 最上部の KillSwitchCard（`稼働中` / `停止中` バッジ、理由・最終更新者を表示） |
| 操作権限 | **`requireAdmin`**。staff はカードを閲覧できるがトグルは拒否される（`AI応答の停止・再開は管理者のみ実行できます`） |
| `#alerts` 通知 | 状態が**変化したときだけ** `SLACK_ALERTS_CHANNEL_ID` へ投稿（見出し / 操作者 / 理由 / 時刻 の 4 行、JST）。未設定なら通知をスキップして `console.warn`。通知失敗でもトグル自体は成功する |
| RLS | `staff_admin_select` の SELECT のみ。書き込みは Service Role 経由 |

### 3.3 日次コスト集計バッチ — 未実装（Phase 2）

DEC-13 により Cron を使わない構成のため、**日次バッチは実装していない**。現状の代替:

- `/admin` ダッシュボードの「今月のコスト」カード — `admin_usage_summary(p_day_start, p_month_start)` RPC が `SUM(estimated_cost)` を DB 側で計算（JST 月初起点）
- `/admin/usage` — `admin_usage_analytics(p_from)` RPC が日次推移 / モデル別 / 生徒別 / エラーコード別を JSONB で返す（JST 暦日）
- 閾値超過時は **人が気づいて** `/admin` の KillSwitchCard から停止する

> 閾値超過の自動検知 → `#alerts` 通知 → 自動停止までを繋ぐには「Cron 不使用制約下での定期起動方式」の設計が要る。
> Phase 2 提案（`docs/05_その他/2026-08-02_Phase2提案.md`）で扱う。

### 3.4 暴走防止のレート制限 — 実装済み

- **person_id 単位: 10回/時**（`RATE_LIMIT_QUESTIONS_PER_HOUR = 10`, `RATE_LIMIT_WINDOW_MS = 1時間`）
  - 実装: `src/features/rate-limit/lib/checkQuestionRateLimit.ts`。`ai_usage_logs` を `person_id` + 直近1時間で count
  - Evaluator 行（`message_ts` が `-eval` 終わり）と要約行（`-summary` 終わり）は**カウントから除外**する
  - 判定は **LLM 呼び出しの前**（画像 DL・RAG よりも前）。超過時は課金を発生させず `RATE_LIMITED` の定型文を返してジョブを `completed` にする
  - 集計失敗時は **fail-open**（制限しない）
- LLM 呼び出し: `max_tokens` を必ず指定（Tutor 1200 / 要約 400 / Evaluator）。`finish_reason='length'` は検出して扱う
- 1リクエストあたりの画像処理上限: 3枚（FR-06 BR-06-02）、1枚 20MB、合計 8MB（`MAX_TOTAL_IMAGE_BYTES`）
- 質問本文: 6000 文字（`MAX_QUESTION_CHARS`）超過は `TOKEN_BUDGET_EXCEEDED`

## 5. インシデント対応 Runbook

### S-01: LLM / Embedding プロバイダ障害
1. `/admin/errors` で `AI_RATE_LIMITED` / `AI_TIMEOUT` / `AI_RESPONSE_FAILED` の急増を確認
2. プロバイダのステータスページを確認
3. `/admin` の KillSwitchCard から **AI応答を停止**（理由を記入 → `#alerts` に自動通知）。生徒には `AI_PAUSED` の定型文が返る
4. 長引く場合は `LLM_BASE_URL` / `LLM_MODEL_*` を別プロバイダに差し替えて再デプロイ（切替後は `MODEL_PRICING` の更新も確認）
5. 復旧確認後、KillSwitchCard から **AI応答を再開**

### S-02: Supabase障害
1. Vercel Logsでタイムアウト急増を検知
2. Supabaseステータスページ確認 (`https://status.supabase.com`)
3. Slack Botが機能停止（DB接続不可のため）。ユーザーへの通知手段なし（許容）
4. 復旧後、`/admin/jobs` で pending / processing の滞留を確認。10〜15分を超えたものはスイープで `JOB_TIMEOUT` として failed 化されるので、そこから「再実行」する

### S-03: コスト暴走
1. `/admin` の「今月のコスト」カード、または `/admin/usage` の生徒別・モデル別内訳で異常を検知（**自動アラートは無い。日次で見る**）
2. 即座に `/admin` の KillSwitchCard から **AI応答を停止**（理由を記入 → `#alerts` 通知）
3. `/admin/usage` の `by_person` / `by_model` で異常な利用源（特定の person_id・モデル）を特定
4. 原因（バグ / 攻撃 / 想定外の利用増）に応じて対処。個別の生徒が原因なら `RATE_LIMIT_QUESTIONS_PER_HOUR` の見直しを検討
5. 単価未登録モデルに切り替えていると `estimated_cost` が 0 で積み上がるので、コストが不自然に小さいときは `MODEL_PRICING` を疑う

### S-04: Slackの未処理ジョブ蓄積
1. `/admin/jobs` の KPI カードで「待機中」「処理中」の件数と**最古の経過時間**を確認
2. 画面を開くと滞留ジョブの回収（スイープ）が自動実行される（60秒スロットル）。すぐ回したい場合は「スイープ実行」ボタン
   - `processing` が 10分超 / `pending` が 15分超 → `failed` + `error_code='JOB_TIMEOUT'` に落として `ai_error_logs` に記録される
3. 失敗の原因を `/admin/errors` で確認（`JOB_TIMEOUT` / `AI_RESPONSE_FAILED` / `SLACK_POST_FAILED` など）
4. 個別ジョブは一覧の「再実行」ボタンから再投入する
   - **二重返信ガード**: 当該スレッドに質問より後の assistant 発言が既にあれば再実行せず `completed` にする
   - 生成済みの `result_text` は保持されるため、再実行しても LLM の再課金は発生しない（配信だけやり直す）
5. **手動 SQL は不要**。`jobs` を直接 UPDATE すると CAS 前提の再実行フローと競合するので避けること

### S-05: AI 応答を止めたまま忘れていた
1. `#alerts` に停止通知が残っているか、`/admin` の KillSwitchCard が `停止中` かを確認
2. 停止中は生徒に `AI_PAUSED` の定型文しか返らない。`ai_error_logs` に `AI_PAUSED`（severity=info）が積まれ続けるので `/admin/errors` でも気づける
3. 再開後、停止中に届いていた質問は自動では処理されない（生徒に再送してもらう）

## 6. 定期メンテナンスタスク

データ保持（1.1）の削除は **Cron ではなく `/admin/jobs` を開いたとき（60秒スロットル）と「スイープ実行」ボタン**で走る（DEC-13 / A-14）。
実装は `src/features/jobs/lib/sweepStaleJobs.ts` の `runJobMaintenance()` = `sweepStaleJobs()` + `cleanupOldRows()`。

| タスク | 頻度 | 実行方法 |
|--------|------|---------|
| 滞留ジョブの回収（`JOB_TIMEOUT` 化） | 自動 | `/admin/jobs` 表示時（60秒スロットル）/ 「スイープ実行」ボタン。processing 10分・pending 15分超が対象、1回あたり各 100 件まで |

| 古い `jobs` レコード削除（7日・completed/skipped/failed のみ） | 自動 | 同上。pending / processing は消さない |
| ジョブ滞留の目視確認 | 日次 | `/admin/jobs` の KPI カード |
| エラーの目視確認・対応済みマーク | 日次 | `/admin/errors`（severity=error / 未対応で絞る） |
