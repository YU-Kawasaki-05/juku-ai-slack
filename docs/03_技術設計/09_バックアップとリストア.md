# バックアップとリストア — juku-ai-slack-bot

> **なぜこの文書があるか**: Supabase を **Free プラン**で運用するため、**自動バックアップが存在しない**。
> 生徒の会話ログ・プロフィール・レポート（個人情報）が消えたら復旧不能で、事故時に塾へ説明できない。
> ロードマップ §3 フェーズ 2-3 の完了条件は「**1 回リストアを試して復元できることを確認した。取れているだけでは不十分**」。
>
> 実装: `scripts/backup-db.sh`（取得）/ `scripts/restore-verify.sql`（リストア後の検証）
> 保存先: **バックアップ専用の private GitHub リポジトリ**（§5 で決定。ワークフロー一式は §6）
> 関連: `docs/03_技術設計/06_運用設計.md` §4、`docs/06_セットアップガイド/step9_運用ガイド.html` §9-7、
> ユーザー側の操作手順は `docs/00_共通/確認事項.md` §3-1

## 0. 大前提（読み飛ばすと事故る）

| # | 制約 | 帰結 |
|---|------|------|
| 1 | **このリポジトリは PUBLIC** | DB 認証情報も、生徒の個人情報を含むダンプも、**このリポジトリには絶対に置かない**。`scripts/backup-db.sh` は `BACKUP_DIR` がリポジトリ内を指していたら実行を拒否する |
| 2 | public リポジトリの GitHub Actions **artifact は認証なしで誰でもダウンロードできる** | バックアップを Actions で回すなら、**認証情報と artifact を持つのは private リポジトリ側**。`.github/workflows/` にバックアップ用ワークフローを置かないのは意図的（§6 に YAML を載せてある） |
| 3 | ダンプには生徒の氏名・会話本文・レポートが**平文で**入る | 保存先は「アクセス権が限定された場所」であることが最低条件。その上で §6-2 のとおり **GPG(AES256) で暗号化してから**置く |
| 4 | **保存先は「バックアップ専用の private GitHub リポジトリ」に決定**（§5） | Cloudflare R2 は不採用（有効化に支払い方法の登録が必要で、デビットカードでは通らなかった）。決定の経緯は §5-1 |
| 5 | private 側のワークフローは **DB の全権認証情報を持つ** | だから public リポジトリを `checkout` して実行しない。スクリプトは private 側に**複製**する（§5-3）。**public 側を更新したら private 側にも反映する** |

## 1. 何が入り、何が入らないか

`scripts/backup-db.sh` は **3 本のファイル**を出力する。1 本でも欠けるとリストアできない。

| ファイル | 中身 | 取得コマンド |
|---|---|---|
| `juku-ai-backup-YYYY-MM-DD-roles.sql` | `anon` / `authenticated` / `authenticator` の `statement_timeout` 設定 | `supabase db dump --role-only` |
| `juku-ai-backup-YYYY-MM-DD-schema.sql` | `public` スキーマの DDL（16 テーブル・RLS ポリシー・RPC・トリガー・インデックス・GRANT） | `supabase db dump` |
| `juku-ai-backup-YYYY-MM-DD-data.sql` | **`public` + `auth` + `storage` の全行**（`COPY` 形式） | `supabase db dump --data-only --use-copy` |
| `juku-ai-backup-YYYY-MM-DD-MANIFEST.txt` | 取得日時・接続先（認証情報なし）・sha256・**テーブルごとの行数** | スクリプトが生成 |

> ⚠️ **最重要の落とし穴**: `supabase db dump` は**既定でスキーマのみ**。`--data-only` を付けないと
> **1 行もデータが入らない**。`step9_運用ガイド.html` に元々書かれていた
> `supabase db dump -f backup.sql --linked` は**スキーマだけのバックアップ**であって、
> これ 1 本では生徒データは 1 件も復元できない。

### 入らないもの

| 対象 | 理由 | 代替 |
|---|---|---|
| **Storage の実ファイル**（`attachments` バケットの画像本体） | DB ダンプは `storage.objects` の**メタデータ行だけ**。リストアすると「行はあるがファイルが無い」状態になる | 重要なら Dashboard → Storage から手動ダウンロード。`step9` §9-7 参照 |
| **環境変数**（Vercel / Slack / LLM のキー） | DB の外 | パスワードマネージャに控える。作り直しで一番困るのがこれ |
| `supabase_migrations.schema_migrations`（migration 履歴） | Supabase CLI が「プラットフォーム管理」として dump 対象外にしている | リストア後に §4 手順 5 で復元する（放置すると次の `db push` が壊れる） |
| `storage.buckets_vectors` / `storage.vector_indexes` | `postgres` ロールに INSERT 権限が無く、**含めるとリストアが丸ごと巻き戻る**（§7-1） | このアプリは使っていない。`BACKUP_EXCLUDE_TABLES` で除外済み |

## 2. なぜ Supabase CLI か（`pg_dump` 直叩きではなく）

**主たる手段は `supabase db dump`（Supabase CLI）**。理由:

1. **pg_dump のバージョン合わせが不要**。本プロジェクトの DB は **PostgreSQL 17**（`supabase/config.toml` の `major_version = 17`）で、
   pg_dump は「サーバより古いクライアント」を拒否する。CLI は **一致するバージョンの pg_dump を Docker 内で動かす**ので、
   実行環境に PostgreSQL クライアントを入れる必要が無い（実際にこの開発機には `pg_dump` が入っていないが問題なく取れる）。
2. **CLI は Supabase 固有のフィルタを持っている**。スキーマ dump からプラットフォーム管理スキーマ（`auth` / `storage` / `realtime` / `extensions` …）の
   DDL を除き、データ dump からは migration 履歴テーブルを除き、先頭に `SET session_replication_role = replica;` を入れて
   **FK・トリガーを無効化した状態で流せる形**にしてくれる。これを手書きの `pg_dump` フラグで再現するのは現実的でない
   （特に `student_episodic_memories.superseded_by` の**自己参照 FK** は、素の `--data-only` では
   「リストアできないかもしれない」と pg_dump 自身が警告する。§7-2）。
3. **追加インストールが不要**。`supabase` は既に devDependency（`package.json`）。`pnpm install` 済みなら `./node_modules/.bin/supabase` が使える。
4. 既存ドキュメント（`step3` / `step9`）が既に Supabase CLI 前提で書かれており、運用者が覚えるツールが増えない。

**両対応にしなかった理由**: 2 つの経路を持つと「片方だけ直してもう片方が壊れている」状態を作る。
特に上記 2 の sed パイプラインは手書きでは再現できないため、`pg_dump` 経路は「CLI と同等」にはならない。
Docker が使えない環境向けの**緊急脱出手段**としてだけ、§7-4 にコマンドを載せてある。

## 3. バックアップの取り方（週次）

```bash
# 認証情報は環境変数だけで渡す。履歴に残したくないので export ではなく 1 行で書く
SUPABASE_DB_URL='postgresql://postgres.xxxxxxxx:PASSWORD@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres' \
  ./scripts/backup-db.sh
```

```bash
# または ref + パスワード（パスワードは自動で percent-encode される）
SUPABASE_PROJECT_REF=xxxxxxxx SUPABASE_DB_PASSWORD='...' ./scripts/backup-db.sh
```

**接続文字列の取得元**: Supabase Dashboard → **⚙ Project Settings → Database → Connection string → `Session pooler` タブ**。
画面の場所と、タブを間違えたときに何が起きるかは **§6-4-1** に詳しく書いてある。

> ⚠️ **`db.<ref>.supabase.co`（Direct connection）は IPv6 専用**。GitHub Actions のランナーは IPv4 なので繋がらない
> （Free プランに IPv4 アドオンは無い）。**Session pooler**（`aws-0-<region>.pooler.supabase.com:5432`、
> ユーザ名が `postgres.<ref>` 形式）の文字列を使うこと。
> Transaction pooler（`:6543`）は `pg_dump` に使えないので選ばない。

| 環境変数 | 既定値 | 用途 |
|---|---|---|
| `SUPABASE_DB_URL` | — | 接続文字列。これがあれば以下は不要 |
| `SUPABASE_PROJECT_REF` / `SUPABASE_DB_PASSWORD` | — | URL 未指定時に必須 |
| `SUPABASE_DB_HOST` / `_PORT` / `_USER` / `_NAME` | `db.<ref>.supabase.co` / `5432` / `postgres` / `postgres` | pooler を使うときに上書き |
| `BACKUP_DIR` | `<repo>/../juku-ai-backups` | 出力先。**リポジトリ内を指すと実行拒否** |
| `BACKUP_MIN_PERSONS` | `1` | `persons` の最小行数。下回ったら失敗 |
| `BACKUP_EXCLUDE_TABLES` | `storage.buckets_vectors storage.vector_indexes` | データ dump から除くテーブル |

### 「取れているつもり」を作らないための仕組み

スクリプトは**すべてのチェックを通るまで最終ファイル名を作らない**。
ダンプは `BACKUP_DIR/.staging-<pid>/` に書き、全チェック合格後に `mv` する。失敗時は staging ごと破棄して**非ゼロ終了**する。

| チェック | 落ちる条件 |
|---|---|
| `supabase db dump` の終了コード | 3 本のうち 1 本でも失敗 |
| ファイルサイズ | schema < 10,000 bytes / data < 1,000 bytes（ダンプが途中で切れた） |
| `CREATE TABLE` の本数 | 16 本未満（**空プロジェクトに繋いだ**） |
| 必須テーブルの名指し確認 | `persons` `reports` `report_chunks` …（16 個）のどれかが schema dump に無い（**接続先を間違えた**） |
| `COPY` ブロック数 | 20 未満 |
| 必須 `COPY` の存在 | `public.persons` / `public.reports` / `public.slack_messages` / `auth.users` / `storage.buckets` |
| `persons` の行数 | `BACKUP_MIN_PERSONS`（既定 1）未満。**データが 1 件も入っていないダンプを成功扱いしない** |

出力例（MANIFEST）:

```
# juku-ai-slack DB backup manifest
created_at_utc : 2026-08-27T08:xx:xxZ
source         : postgresql://<host>:5432/postgres
supabase_cli   : 2.107.0
public_tables  : 16
copy_blocks    : 46
excluded_data  : storage.buckets_vectors storage.vector_indexes

## files (リストアはこの順に psql で流す)
juku-ai-backup-2026-08-27-roles.sql      297 bytes  sha256=...
juku-ai-backup-2026-08-27-schema.sql   94820 bytes  sha256=...
juku-ai-backup-2026-08-27-data.sql     33091 bytes  sha256=...

## row counts
public.persons               2
public.reports               1
...
auth.users                   1
```

**MANIFEST の row counts は捨てないこと。** リストア後にこの数字と突き合わせるのが「復元できた」の判定根拠になる。

## 4. リストア手順（本番想定）

**前提**: 対象は「まっさらな Supabase プロジェクト」（作り直した新プロジェクト、または検証用プロジェクト）。
既存プロジェクトに上書きしようとすると重複キーで巻き戻るだけなので、**必ず空の DB に流す**。

### 手順 0. 使う道具

`psql` が要る。macOS で PostgreSQL クライアントを入れていない場合は Docker で代用できる（**この手順は実測済み**）:

```bash
PSQL() { docker run --rm -i -v "$PWD:/backup:ro" \
  public.ecr.aws/supabase/postgres:17.6.1.136 psql "$@"; }
```

以降 `PSQL` はこの関数（またはローカルの `psql`）を指す。`-v ON_ERROR_STOP=1 --single-transaction` は必ず付ける
（**エラーで止まらないと「半分だけ復元された DB」ができる**。これが一番危険な状態）。

### 手順 1. バックアップの完全性を確認する

> 🔑 artifact / Releases から取ってきた世代は `*.sql.gpg`（GPG 暗号化済み）。**先に復号する**:
> `printf '%s' "$PASSPHRASE" | gpg --batch --pinentry-mode loopback --passphrase-fd 0 -o FOO.sql -d FOO.sql.gpg`
> パスフレーズは private リポジトリの Secret `BACKUP_GPG_PASSPHRASE`（§6-4）。
> MANIFEST に載っている sha256 は**復号後の平文**のもの。復号してから照合すれば一致する（実測確認済み）。
> `*-MANIFEST.txt` は暗号化していないので、復号前に行数だけ見ることもできる。

```bash
cd <バックアップの置き場>
shasum -a 256 juku-ai-backup-2026-08-27-*.sql     # Linux なら sha256sum
grep -c '^CREATE TABLE' juku-ai-backup-2026-08-27-schema.sql   # → 16
grep -c '^COPY '        juku-ai-backup-2026-08-27-data.sql     # → 46 前後
```

MANIFEST の sha256 と一致しなければ、その世代は使わず前の世代を使う。

### 手順 2. ロール設定を流す

```bash
PSQL "$TARGET_DB_URL" -v ON_ERROR_STOP=1 --single-transaction \
  -f /backup/juku-ai-backup-2026-08-27-roles.sql
```

### 手順 3. スキーマを流す

```bash
PSQL "$TARGET_DB_URL" -v ON_ERROR_STOP=1 --single-transaction \
  -f /backup/juku-ai-backup-2026-08-27-schema.sql
```

`vector` / `pgcrypto` / `uuid-ossp` / `pg_net` の `CREATE EXTENSION` もこの中に入っている。

### 手順 4. データを流す

```bash
PSQL "$TARGET_DB_URL" -v ON_ERROR_STOP=1 --single-transaction \
  -f /backup/juku-ai-backup-2026-08-27-data.sql
```

先頭の `SET session_replication_role = replica;` が FK・トリガーを止めるので、
**テーブルの投入順序や自己参照 FK を気にする必要は無い**（気にしなければならないのは §7-2 のとおり素の `pg_dump` を使ったとき）。

### 手順 5. migration 履歴を復元する（忘れると次のデプロイで壊れる）

ダンプに `supabase_migrations.schema_migrations` は入っていない。放置すると
`supabase db push` が「32 本とも未適用」と判断して全部流し直そうとする。

```bash

  017 018 019 020 021 022 023 024 025 026 027 028 029 030 031 032
```

### 手順 6. 「復元できた」の判定

```bash
# psql が入っているなら（リポジトリのルートで）
psql "$TARGET_DB_URL" -f scripts/restore-verify.sql
```

```bash
# psql が無い場合。手順 0 の PSQL 関数はバックアップ置き場をマウントしているので、
# ここは scripts/ をマウントし直す（実測済みのコマンド形）
docker run --rm -i -v "<repo>/scripts:/s:ro" \
  public.ecr.aws/supabase/postgres:17.6.1.136 \
  psql "$TARGET_DB_URL" -f /s/restore-verify.sql
```

`scripts/restore-verify.sql` が 7 ブロックを出す。**すべて満たして初めて「復元できた」**:

| # | 見るもの | 合格条件 |
|---|---|---|
| 1 | スキーマの規模 | テーブル 16 / RLS 有効 16 / ポリシー 16 / インデックス 61 / トリガー 10 / migration 履歴 32 |
| 2 | 必須テーブルの欠落 | **0 行** |
| 3 | 必須の関数・拡張の欠落 | **0 行**（`match_report_chunks` / `rebuild_report_chunks` / `is_staff_or_admin` / `admin_*` / `vector` …） |
| 4 | 行数 | **バックアップの MANIFEST の row counts と一致** |
| 5 | 中身の健全性 | `embedding` が 1536 次元 / 自己参照 FK の参照先が存在 / 日本語が化けていない / `service_role` は読めて `anon` は読めない |
| 6 | RAG の RPC | `match_report_chunks` が 1 件以上返す（chunk が 0 件なら SKIP） |
| 7 | Storage | `storage.objects` の行数を確認し、**実ファイルが無いこと**を認識する |

さらに**アプリを繋いで**次の 3 つを目視するところまでやる:

- `/login` でスタッフがログインできる（= `auth.users` が戻っている）
- `/admin` の生徒一覧が出る
- Slack で 1 件質問して回答が返る（= RAG と `kill_switches` が生きている）

> ⚠️ `restore-verify.sql` の期待値（インデックス 61 / トリガー 10 など）は **migration 032 時点**の値。
> migration を追加したらこの数字と表を更新する。

## 5. 保存先 — **バックアップ専用の private GitHub リポジトリ**（決定）

`scripts/backup-db.sh` は**ローカルのディレクトリに出すところまで**を担当する。その先の「どこへ置くか」は、
**このリポジトリとは別に作る、バックアップ専用の private リポジトリ**にする。

### 5-1. なぜこの構成にしたか（不採用にした案も残す）

| 案 | 結論 | 理由 |
|---|---|---|
| public リポジトリ（＝このリポジトリ）の Actions artifact | **不採用** | public リポジトリの artifact は**認証なしで誰でもダウンロードできる**。未成年の氏名・会話ログ・レポートを置ける場所ではない |
| Cloudflare R2 / S3 | **不採用** | 技術的には最適（egress 無料・10GB 無料枠）だが、**R2 の有効化に支払い方法の登録が必要で、デビットカードでは通らなかった**。無料枠内でも登録自体が必須のため、この環境では使えない |
| **バックアップ専用の private リポジトリ** | **採用** | GitHub Free は**カード登録が不要**で、private リポジトリ無制限・Actions 2,000 分/月・artifact 500MB が無料。artifact のダウンロードには**リポジトリの read 権限が要る**ので、コラボレータを足さない限り閲覧できるのはオーナーだけ |
| 運用者の PC で手動実行 | 併用しない | 一番安いが**忘れる**。週次を人手に依存させない |

**無料枠に収まるか**（GitHub Free）

| 項目 | 無料枠 | 今回の使用量 |
|---|---|---|
| Actions 実行時間（private） | 2,000 分/月 | 1 回 2〜4 分 × 月 4〜5 回 ≒ **20 分/月** |
| artifact ストレージ | 500 MB | 1 世代 約 130 KB（現状）× 13 世代 ≒ **2 MB** |
| private リポジトリ数 | 無制限 | 1 |
| Releases のアセット | 容量課金なし（1 ファイル 2 GiB 上限） | 月 1 世代 |

> ⚠️ **artifact ストレージだけは将来詰まりうる。** ダンプは生徒数と会話量に比例して増える。
> MANIFEST のファイルサイズを見て、**1 世代が 30 MB を超えたら** `retention-days` を短くするか、
> 週次 artifact をやめて Releases 主体に切り替える（§6-5）。

### 5-2. 何がどこにあるか

```
public: <owner>/marujuku-slack                private: <owner>/juku-ai-backup
├── scripts/backup-db.sh        ── 複製 ──→   ├── scripts/backup-db.sh        ← 同一内容のコピー
├── scripts/restore-verify.sql  ── 複製 ──→   ├── scripts/restore-verify.sql  ← 同一内容のコピー
└── docs/03_技術設計/09_...md（この手順書）    ├── .github/workflows/backup.yml（§6-2）
                                               ├── README.md（§6-7）
                                               └── Secrets: SUPABASE_DB_URL ほか（§6-4）
                                                    │ 毎週 実行
                                                    ├→ Actions artifact（90 日で自動削除）
                                                    └→ 月初だけ Releases（保持期限なし）
```

**この 2 つのリポジトリの間に、実行時の依存は無い。** private 側は自分の中のファイルだけで完結する。

### 5-3. なぜスクリプトを「複製」するのか（public を checkout しないのか）

⚠️ **ここが今回のセキュリティ上の要点。**

private 側のワークフローは **DB の接続文字列（＝本番 DB への全権アクセス）を Secrets として持つ**。
このワークフローが public リポジトリを `actions/checkout` してそこのスクリプトを実行する構成にすると、
**public リポジトリに書き込める者は、認証情報を持ったランナー上で任意のコードを実行できる**ことになる。
`backup-db.sh` に 1 行足して `SUPABASE_DB_URL` を外部へ POST すれば、それで終わる。
public リポジトリはコントリビュータの受け入れや PR の取り込みで書き込み経路が増えていく場所なので、
**そこを本番 DB の認証情報の上流に置かない。**

- コミット SHA でのピン留めは**緩和にはなる**（ref を固定すれば後からの書き換えは反映されない）。
  ただし「スクリプトを更新するたびに、人が中身を確認して SHA を差し替える」運用が前提になり、
  **確認を省いた 1 回で穴が開く**。緩和策であって、経路そのものは残る。
- **複製すれば、その依存関係自体が存在しなくなる。** `backup-db.sh` は外部ライブラリを持たない
  自己完結の bash スクリプトで、更新頻度も低い（migration 追加時に定数を見直す程度）。
  複製のコストは、この経路を丸ごと消せることに対して十分小さい。

> 📌 **運用注意 — スクリプトを更新したら private 側にも反映する**
> `scripts/backup-db.sh` と `scripts/restore-verify.sql` を**このリポジトリで更新したら、
> 同じ変更を private リポジトリにもコピーする。** 反映を忘れると
> 「public 側は直っているのに、毎週実際に動いているのは古いスクリプト」という、
> 手元の差分を見ても気づけない状態になる。
> 特に **migration を追加したとき**は `REQUIRED_TABLES` / `BACKUP_MIN_TABLES` と
> `restore-verify.sql` の期待値がずれる。§9 の「migration 追加時」の行にこの反映作業を入れてある。

### 6-2. `.github/workflows/backup.yml`

````yaml
# .github/workflows/backup.yml
# ⚠️ このファイルは「バックアップ専用の private リポジトリ」に置く。
#    公開リポジトリ（marujuku-slack）には置かない。
name: Weekly DB backup

on:
  schedule:
    # 日曜 18:35 UTC = 月曜 03:35 JST（JST に夏時間は無いので通年ズレない）
    # ・毎時 00 分は GitHub 側が混みやすく schedule が遅延しやすいので 35 分にずらす
    # ・月曜未明に回すと、失敗通知を「週の頭の朝」に受け取れる（週末に放置されない）
    - cron: '35 18 * * 0'
  workflow_dispatch:
    inputs:
      archive_to_release:
        description: 'Releases にも保存する（月次アーカイブを手で作り直すとき）'
        type: boolean
        default: false

permissions:
  contents: write        # Releases への添付に必要。それ以外の権限は与えない

concurrency:
  group: backup-db
  cancel-in-progress: false

jobs:
  backup:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      # スクリプトはこの private リポジトリ自身に複製してある。
      # 公開リポジトリを checkout しないのが要点（理由は §5-3）。
      - uses: actions/checkout@v4
        with:
          persist-credentials: false

      - uses: supabase/setup-cli@v1
        with:
          version: 2.107.0      # リストア訓練で使ったバージョン。上げるときは手動実行で1回試す

      - name: Dump
        env:
          # Session pooler の接続文字列。Direct connection は IPv6 専用でランナーから繋がらない
          SUPABASE_DB_URL: ${{ secrets.SUPABASE_DB_URL }}
          SUPABASE_CLI: supabase
          BACKUP_DIR: ${{ runner.temp }}/backup
          BACKUP_MIN_PERSONS: '1'   # persons が 0 行なら失敗させる（空ダンプを成功扱いしない）
        run: ./scripts/backup-db.sh

      # 週次の目視確認を「Summary を開くだけ」で済ませる。
      # row counts が前週より不自然に減っていないかを見るのが目的。
      - name: Publish manifest to job summary
        env:
          BACKUP_DIR: ${{ runner.temp }}/backup
        run: |
          set -euo pipefail
          {
            echo '## backup manifest'
            echo '```'
            cat "$BACKUP_DIR"/*-MANIFEST.txt
            echo '```'
          } >> "$GITHUB_STEP_SUMMARY"

      - name: Encrypt
        env:
          BACKUP_DIR: ${{ runner.temp }}/backup
          PASSPHRASE: ${{ secrets.BACKUP_GPG_PASSPHRASE }}
        run: |
          set -euo pipefail
          if [ -z "$PASSPHRASE" ]; then
            echo "::error::BACKUP_GPG_PASSPHRASE が未設定" >&2
            exit 1
          fi
          cd "$BACKUP_DIR"
          shopt -s nullglob
          files=(*.sql)
          if [ "${#files[@]}" -eq 0 ]; then
            echo "::error::暗号化対象の .sql が無い" >&2
            exit 1
          fi
          for f in "${files[@]}"; do
            printf '%s' "$PASSPHRASE" | gpg --batch --yes --quiet \
              --pinentry-mode loopback --passphrase-fd 0 \
              --symmetric --cipher-algo AES256 -o "$f.gpg" "$f"
            rm -f "$f"
          done
          ls -l

      - uses: actions/upload-artifact@v4
        with:
          name: juku-ai-db-backup-${{ github.run_id }}
          path: ${{ runner.temp }}/backup
          retention-days: 90        # private リポジトリの上限は 400。90 にした理由は §6-5
          if-no-files-found: error

      # 月初の実行だけ Releases に積む（Releases は保持期限が無い）。
      # 週次は月曜なので、UTC 日付が 1〜7 日に当たる実行は月にちょうど 1 回。
      - name: Archive to Releases
        env:
          BACKUP_DIR: ${{ runner.temp }}/backup
          EVENT_NAME: ${{ github.event_name }}
          FORCE_ARCHIVE: ${{ inputs.archive_to_release }}
          GH_TOKEN: ${{ github.token }}
        run: |
          set -euo pipefail
          if [ "$EVENT_NAME" = "schedule" ]; then
            day="$(date -u +%d)"
            if [ "$((10#$day))" -gt 7 ]; then
              echo "月初（UTC 1〜7 日）ではないので Releases への保存はスキップ"
              exit 0
            fi
          elif [ "$FORCE_ARCHIVE" != "true" ]; then
            echo "手動実行かつ archive_to_release=false なのでスキップ"
            exit 0
          fi
          tag="backup-$(date -u +%Y-%m)"
          if ! gh release view "$tag" >/dev/null 2>&1; then
            gh release create "$tag" --title "$tag" \
              --notes "月次 DB バックアップ（自動）。復号は BACKUP_GPG_PASSPHRASE。" --latest=false
          fi
          gh release upload "$tag" "$BACKUP_DIR"/* --clobber

      # 落ちたことに気づかないのが最悪。GitHub のメール通知に加えて #alerts にも出す。
      - name: Notify failure
        if: failure()
        env:
          SLACK_WEBHOOK: ${{ secrets.SLACK_ALERTS_WEBHOOK_URL }}
        run: |
          set -euo pipefail
          if [ -z "$SLACK_WEBHOOK" ]; then
            echo "SLACK_ALERTS_WEBHOOK_URL 未設定。Slack 通知はスキップ（GitHub のメール通知のみ）"
            exit 0
          fi
          run_url="$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
          payload="$(printf '{"text":":rotating_light: 週次 DB バックアップが失敗しました\n%s"}' "$run_url")"
          curl -sS --fail-with-body -X POST -H 'Content-Type: application/json' \
            -d "$payload" "$SLACK_WEBHOOK"
````

> **アクションのピン留めについて**: `actions/*` は GitHub 自身が管理しているので `@v4` のままでよい。
> `supabase/setup-cli` はサードパーティなので、運用が固まったら SHA に差し替える:
> `gh api repos/supabase/setup-cli/commits/v1 --jq .sha` の結果を `@<sha>` として書く。
> なお `version: 2.107.0` の指定で、**取得される supabase CLI 本体は既に固定されている**。

### 6-3. cron をこの値にした理由（JST 換算の検算つき）

`'35 18 * * 0'` = **日曜 18:35 UTC**。GitHub Actions の cron は**常に UTC**で解釈される。

| | 値 |
|---|---|
| UTC | 日曜 18:35 |
| JST（UTC+9） | **月曜 03:35** |
| 通年ブレるか | **ブレない**。日本には夏時間が無く JST は常に UTC+9（400 週分を計算して曜日・時刻が `Mon 03:35` から動かないことを確認済み） |
| 年間実行回数 | 52 回 |

決めた理由:

1. **月曜未明（JST）にする** — 失敗通知が「週の頭の朝」に届く。土曜に回すと失敗が週末いっぱい放置される。
2. **深夜帯にする** — 塾の利用は夕方〜夜。03:35 JST は DB が最も静かで、pooler の接続枠を生徒と奪い合わない。
3. **`00` 分を避ける** — GitHub の公式ドキュメントが「schedule は高負荷時に遅延することがあり、毎時の始まりが特に混む。
   遅延を減らすには時刻をずらせ」と明記している。`35` 分にしてある。
4. **`schedule` は best-effort** — 数十分ずれることも、混雑時にスキップされることもある。
   **時刻の厳密さに依存しない設計**（週次バックアップなので数十分のずれは無害）。ずれが続くなら
   `workflow_dispatch` で手動実行できる。

> ✅ **private リポジトリなので「60 日無活動で schedule が自動停止」の対象外**。
> GitHub のこの仕様は「**public リポジトリでは**、60 日間リポジトリに活動が無いと scheduled workflow が
> 自動的に無効化される」というもので、private リポジトリには適用されない。
> コミットが発生しないバックアップ専用リポジトリでも、勝手に止まらない。

### 6-4. 必要な Secrets

private リポジトリの **Settings → Secrets and variables → Actions → New repository secret** で登録する。

| Secret 名 | 必須 | 何を入れるか / 取得場所 |
|---|---|---|
| `SUPABASE_DB_URL` | ✅ | **Session pooler の接続文字列**。取得場所は §6-4-1 |
| `BACKUP_GPG_PASSPHRASE` | ✅ | 自分で生成する 32 文字以上のランダム文字列（例: `openssl rand -base64 32`）。**パスワードマネージャに必ず控える。失うとバックアップが復号できず、バックアップが無いのと同じになる** |
| `SLACK_ALERTS_WEBHOOK_URL` | 任意 | `#alerts` 向けの Slack Incoming Webhook URL。未設定なら Slack 通知だけスキップされ、GitHub のメール通知は届く |

`GITHUB_TOKEN` は登録不要（GitHub が自動で発行する。ワークフロー側で `permissions: contents: write` を宣言済み）。

#### 6-4-1. `SUPABASE_DB_URL` の取得場所（画面の場所）

1. https://supabase.com/dashboard で対象プロジェクトを開く
2. 左サイドバーの一番下 **⚙ Project Settings** → **Database**
3. **Connection string** のセクションまでスクロールする
4. タブが **`Direct connection` / `Transaction pooler` / `Session pooler`** に分かれている。
   → **`Session pooler` タブを選ぶ**
5. 表示されている `postgresql://postgres.<ref>:[YOUR-PASSWORD]@aws-0-<region>.pooler.supabase.com:5432/postgres`
   をコピーし、**`[YOUR-PASSWORD]` の部分を実際の DB パスワードに置き換えて**から Secret に貼る
   （パスワードを忘れた場合は同じ画面の **Database password → Reset database password** で再発行できる。
   再発行すると既存の接続文字列は無効になるので、他に使っている場所がないか確認してから行う）

⚠️ **タブの選択を間違えると動かない。**

| タブ | ホスト | 使えるか |
|---|---|---|
| Direct connection | `db.<ref>.supabase.co:5432` | ❌ **IPv6 専用**。GitHub Actions のランナーは IPv4 なので接続できない（Free プランに IPv4 アドオンは無い） |
| Transaction pooler | `...pooler.supabase.com:6543` | ❌ prepared statement を張れないので `pg_dump` が使えない |
| **Session pooler** | `...pooler.supabase.com:5432` | ✅ **これを使う**。ユーザ名が `postgres.<ref>` 形式になっているのが目印 |

> パスワードに `@` `:` `/` `#` などの記号が入っている場合は、**percent-encode してから**貼る
> （`@` → `%40` など）。エンコードが面倒なら、`SUPABASE_DB_URL` の代わりに
> `SUPABASE_PROJECT_REF` / `SUPABASE_DB_PASSWORD` / `SUPABASE_DB_HOST` / `SUPABASE_DB_USER` を
> 個別に渡す方式にすれば、スクリプト側が自動でエンコードする（`backup-db.sh` の `urlencode`）。

### 6-5. 保持期間と世代管理 — **週次 artifact 90 日 ＋ 月初を Releases に無期限（棚卸しは 24 か月）**

**推奨値はこれ。** 迷ったらこのまま使う。

| 経路 | 設定 | 世代数 |
|---|---|---|
| 週次 → Actions artifact | `retention-days: 90` | 約 **13 世代**（直近 3 か月ぶんの週次） |
| 月初 → Releases | 保持期限なし。**24 か月分を残す** | 24 世代（月次） |

理由:

1. **artifact は保持期間を過ぎると GitHub が自動削除する。手動での延長はできない。**
   だから「長期保存は Releases」と経路を分ける。Releases のアセットには保持期限が無い。
2. **90 日にした理由（400 日まで伸ばせるのに伸ばさない理由）** — 保存しているのは未成年の氏名・会話ログ・
   レポートの**平文コピー**（暗号化していても、パスフレーズを持つ人にとっては平文と同じ）。
   **個人情報のコピーは必要以上に長く滞留させない**のが原則。
   加えて、90 日より古い世代に「週次」の粒度は要らない。その帯域は Releases の月次で足りる。
3. **月初の 1 本だけ Releases に上げる理由** — 「壊れたデータを上書きバックアップした」ことに数か月後に
   気づくケース（誤削除・不正な一括更新）に備える。週次を全部長期保存すると量も PII 滞留も増えるだけで、
   その帯域では月次の粒度で十分。
4. **24 か月で棚卸しする理由** — 塾の在籍サイクル（中 3 / 高 3 で 3 年）を踏まえても、
   退塾済みの生徒データを無期限に持ち続ける理由が無い。年 1 回、24 か月より古い Release を削除する
   （`gh release delete backup-YYYY-MM --yes --cleanup-tag`）。§9 の年次作業に入れてある。

> ⚠️ **artifact はリポジトリの read 権限がある全員がダウンロードできる。** private リポジトリでも
> 「コラボレータを足した瞬間、その人に生徒の個人情報が開示される」ことを意識する
> （だから GPG 暗号化を必須にしている）。**このリポジトリにコラボレータを追加しない。**

### 6-6. 「成功したが中身が空」を検知できるか — **できる（実測で確認済み）**

ワークフローが失敗すれば GitHub からメールが届く。問題は「**ワークフローは緑なのに、中身が空**」のほう。
`scripts/backup-db.sh` が**この場合に非ゼロ終了する実装になっていること**を、スタブ CLI で実際に確かめた
（2026-08-30 実測）。

| 与えた状況 | 期待 | 実測 |
|---|---|---|
| `persons` が **0 行**のデータダンプ（COPY ブロックは 35 本ある＝一見それらしい） | 失敗 | **exit 1** / `FATAL: persons が 0 行（期待 1 行以上）。データが入っていないダンプを成功扱いしない` / **出力ファイル 0 個**（staging ごと破棄） |
| データダンプが途中で切れた（40 bytes） | 失敗 | **exit 1** / `FATAL: データダンプ が小さすぎる（40 bytes < 1000）` / 出力ファイル 0 個 |
| 正常なダンプ | 成功 | **exit 0** / 4 ファイル出力 / MANIFEST に `public.persons 2` |
| （併せて確認）ログに接続文字列のパスワードが混ざらないか | 混ざらない | 3 ケースとも**平文パスワードの出現 0 回**（`scrub` が効いている） |

したがって **「空ダンプが artifact として上がる」ことは起きない**。スクリプトが落ちればジョブが落ち、
`if-no-files-found: error` も二重の網になる。

**それでも残る穴**（正直に書いておく）: 行数の下限を持っているのは `persons` だけ。
「`persons` は残っているが `slack_messages` が全部消えた」は**スクリプトでは検知できない**。
これを人の目で拾うために、ワークフローに **MANIFEST をジョブサマリに出す**ステップを入れてある。
毎週 Actions の run を開いて **row counts が前週より不自然に減っていないか**だけ見る（10 秒で済む）。
運用が安定したら `BACKUP_MIN_PERSONS` を実際の生徒数に近い値へ引き上げると、網がもう一段細かくなる。

## 7. 既知の落とし穴（実測で踏んだもの）

### 7-1. `permission denied for table buckets_vectors`

データ dump をそのまま流すと、`postgres` ロールに INSERT 権限が無い Storage 内部テーブルで止まる。
`--single-transaction` を付けていると**トランザクションが丸ごと巻き戻り、1 行も入らない**。

- 対象は `storage.buckets_vectors` と `storage.vector_indexes`（Storage のベクトルバケット機能の内部テーブル。本アプリは未使用）
- **対策済み**: `scripts/backup-db.sh` が `BACKUP_EXCLUDE_TABLES` の既定値でこの 2 つを dump から除外する
- **既に取ってしまったダンプで踏んだ場合**（再取得できない状況）は、該当 `COPY` ブロックを落としてから流す:

```bash
awk '/^COPY "storage"\."(buckets_vectors|vector_indexes)" /{skip=1} skip&&/^\\\.$/{skip=0;next} !skip' \
  in-data.sql > out-data.sql
```

- 将来 Storage / Auth が同種のテーブルを増やしたら、同じエラーが別名で出る。
  `BACKUP_EXCLUDE_TABLES` に足して再取得する。権限の確認は次のクエリ:

```sql
select c.relnamespace::regnamespace || '.' || c.relname,
       has_table_privilege('postgres', c.oid, 'INSERT') as can_insert
  from pg_class c
 where c.relkind = 'r'
   and c.relnamespace::regnamespace::text in ('storage', 'auth')
 order by 2, 1;
```

### 7-2. 自己参照 FK の循環警告

データ dump のたびに pg_dump が出す（**エラーではない**）:

```
pg_dump: warning: there are circular foreign-key constraints on this table:
pg_dump: detail: student_episodic_memories
pg_dump: hint: You might not be able to restore the dump without using --disable-triggers ...
```

`student_episodic_memories.superseded_by` が同じテーブルを参照しているため。
**Supabase CLI のデータ dump は先頭に `SET session_replication_role = replica;` を入れるので実害は無い**
（リストア検証で `superseded_by` の参照先が正しく戻ることを確認済み）。
素の `pg_dump --data-only` を使う場合は `--disable-triggers` が必要になる。

### 7-3. `SET session_replication_role` が拒否されたら

権限が足りない環境ではこの `SET` が失敗し得る。その場合はデータ投入中だけ FK を遅延させる:

```sql
begin;
set constraints all deferred;   -- DEFERRABLE な制約にしか効かない点は注意
\i data.sql
commit;
```

これでも通らない場合は、`public` のデータだけ先に流し（`--schema public` で取り直す）、
`auth.users` は**スタッフを招待し直す**（2〜3 名なので現実的）方が速い。

### 7-4. Docker が使えない環境での緊急脱出（`pg_dump` 直叩き）

Supabase CLI は pg_dump を Docker で動かす。Docker が無い環境では次のようにする。
**PostgreSQL 17 のクライアント**が必要（古い pg_dump はサーバ側が新しいと拒否される）。

```bash
pg_dump "$SUPABASE_DB_URL" --schema-only \
  --exclude-schema='auth|storage|realtime|extensions|graphql|graphql_public|vault|supabase_migrations|pgbouncer|_analytics|_realtime|_supavisor|net|supabase_functions' \
  -f schema.sql

pg_dump "$SUPABASE_DB_URL" --data-only --disable-triggers \
  --exclude-table='auth.schema_migrations' \
  --exclude-table='storage.migrations' \
  --exclude-table='storage.buckets_vectors' \
  --exclude-table='storage.vector_indexes' \
  --exclude-schema='supabase_migrations|realtime|extensions|_analytics|_realtime|_supavisor|vault' \
  -f data.sql
```

これは **CLI 出力と完全に同等ではない**（所有者・ACL の扱いが違い、リストア時に手直しが要る場合がある）。
あくまで「CLI が動かないときだけ」の手段。通常は CLI を使う。

### 7-5. ローカル検証時のホスト名

- `supabase db dump` は pg_dump を **Docker コンテナ内**で動かすため、ホストの DB を指すには
  `host.docker.internal:<port>` を使う（`127.0.0.1` はコンテナ自身を指してしまう）。
- `supabase migration repair` は **CLI プロセスから直接**接続するので `127.0.0.1` 側。
  ただし `--db-url` 指定時は TLS を要求するため、TLS 無効なローカル DB には繋がらない（§4 手順 5 の方法 B を使う）。
- 本番の Supabase 相手ならどちらも同じホスト名で動くので、この区別が問題になるのはローカル検証のときだけ。
