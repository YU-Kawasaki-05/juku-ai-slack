STEP 3 — DB マイグレーション適用

ローカルの作業マシンから Supabase CLI で supabase/migrations/ の 32 本を本番プロジェクトに流し込みます。 テーブル 16 本・関数 9 本・Storage バケット 1 つ・pgvector 拡張が作られます。

所要時間約 15 分
前提Node.js 22 以上 / pnpm 10.6 以上（推奨 11） / STEP 2 完了
このステップで手に入るものスキーマが適用された本番 DB

3-1. リポジトリを用意して依存をインストール

git clone <あなたのリポジトリURL> juku-ai-slack
cd juku-ai-slack
pnpm install

pnpm 11 での注意: pnpm install が ERR_PNPM_IGNORED_BUILDS で止まる場合、 ビルドスクリプト許可リストが読めていません。pnpm-workspace.yaml に allowBuilds（pnpm 11 用）と onlyBuiltDependencies（pnpm 10 用）の 両方が入っていることを確認してください（esbuild / msw / sharp / unrs-resolver）。 pnpm 10.6 以降は package.json の "pnpm" フィールドを読まないため、この設定はワークスペースファイル側に置いています。

3-2. Supabase CLI にログインしてプロジェクトをリンク

CLI はリポジトリの devDependency に入っているので、グローバルインストールは不要です（pnpm exec で呼びます）。

# ブラウザが開いて認証トークンを発行する
pnpm exec supabase login

# STEP 2 で控えた Project Ref を指定
pnpm exec supabase link --project-ref <あなたのProjectRef>

link の途中で Database password を聞かれます。STEP 2-1 で控えた DB パスワードを入力してください （入力しても画面には表示されません）。

パスワードを紛失した場合は Project Settings → Database → Database password → Reset database password で再発行できます。 再発行しても既存のデータは消えません。

3-3. マイグレーションを適用する

pnpm exec supabase db push

適用予定の migration 一覧（001〜032）が表示され、確認を求められます。Y で実行してください。

主な migration内容
001〜013基本テーブル（生徒・レポート・チャンネル紐付け・セッション・メッセージ・添付・利用ログ・エラーログ・受信記録・ジョブ）
004 / 005pgvector 拡張 + report_chunks.embedding vector(1536)
014 / 015全テーブル RLS 有効化 + 初期ポリシー
020 / 021ベクトル検索 RPC match_report_chunks（承認済み・送信済みレポートのみ参照）
022Storage バケット attachments（非公開）を作成
026RLS 強化。authenticated は staff/admin の SELECT のみに。サインアップ無効化とセット
029管理画面の集計 RPC（admin_usage_summary ほか 3 本）
031kill_switches テーブル + 初期行 ai_responses（enabled = true）
032ジョブのスイープ／掃除用インデックス

Cron は使いません。滞留ジョブの回収と古い記録の掃除は、スタッフが /admin/jobs を開いたときと手動ボタンで実行されます（設計判断 DEC-13）。 pg_cron や Vercel Cron の設定は不要です。

3-4. 適用結果を確認する

Supabase ダッシュボードの SQL Editor で以下を実行します。

① テーブルが 16 本あるか

select table_name
from information_schema.tables
where table_schema = 'public' and table_type = 'BASE TABLE'
order by table_name;

期待される 16 本:

ai_error_logs, ai_usage_logs, attachments, jobs, kill_switches, learning_concepts, persons, report_chunks, reports, slack_channel_bindings, slack_event_receipts, slack_messages, slack_thread_sessions, student_episodic_memories, student_knowledge_states, student_profiles

② pgvector が有効か

select extname, extversion from pg_extension where extname = 'vector';

1 行返れば OK。返らない場合は 004_enable_pgvector.sql が流れていません。

③ attachments バケットが「非公開」で存在するか

select id, name, public from storage.buckets where id = 'attachments';

public が false であることを必ず確認してください。true だと生徒が送った画像が URL を知る誰にでも見えます。

④ kill_switches の初期行があるか

select name, enabled, reason, updated_at from kill_switches;

ai_responses / enabled = true の 1 行が返れば OK。

この行が無くても Bot は動きます（読み取れないときは fail-open = 稼働中とみなす設計）。 「kill switch 自体の障害で全生徒の質問が止まる方が事故として重い」ためです。ただし管理画面からの停止操作を確実にするため、行は作っておいてください。

⑤ RLS が全テーブルで有効か

select relname, relrowsecurity
from pg_class
where relnamespace = 'public'::regnamespace and relkind = 'r'
order by relname;

16 行すべて relrowsecurity = true であることを確認します。

⑥ 適用済み migration の本数

select count(*) from supabase_migrations.schema_migrations;

32 になっていれば全部流れています。
