STEP 9 — 運用ガイド（引き渡し前に読む）

ここは塾側の担当者に説明する内容です。セットアップした本人だけが知っている状態にせず、 このページを一緒に見ながら引き渡してください。

所要時間約 15 分（説明を含む）
対象塾の運用担当者（staff）と管理者（admin）

9-1. 緊急停止（一番最初に教えること）

「AI が変なことを言っている」「コストが暴れている」ときに、まずやるのはこれです。 デプロイも環境変数の変更も不要で、数秒で全生徒への回答を止められます。

止め方

  1. /admin を開く（ダッシュボードの一番上に AI応答 カードがあります）
  2. AI応答を停止 をクリック
  3. 理由を入力（例 LLM プロバイダ障害のため一時停止）— 任意ですが必ず書いてください。#alerts と管理画面に残ります
  4. 停止する
項目内容
誰ができるかadmin のみ。staff はカードを見られるが操作すると AI応答の停止・再開は管理者のみ実行できます で拒否される
止まると何が起きるか🤔 も付かず、質問には定型文だけが返る:
いまメンテナンス中でお返事ができないんだ :bow: しばらく経ってからもう一度質問してね。
LLM は呼ばれないので課金も止まります
通知SLACK_ALERTS_CHANNEL_ID を設定していれば #alerts に「操作者・理由・時刻」が投稿される。 状態が変わったときだけ通知される（同じ操作の連打では飛ばない）
再開同じカードの AI応答を再開。カードが緑の 稼働中 に戻る
止まらなかった場合スイッチが読めないときは安全側ではなく稼働側に倒れる設計（全生徒が突然無応答になる事故を避けるため）。 どうしても止められないときは Vercel のデプロイを停止するか、Slack アプリのイベント購読を Off にする

停止したことを忘れないでください。ダッシュボードを開けばカードが赤い 停止中 になっているので、 朝いちばんに /admin を見る運用にしておくと取りこぼしません。

9-2. レート制限（生徒 1 人あたり 10 回 / 時）

1 人の生徒が直近 1 時間に 10 回回答を受け取ると、それ以降の質問には次の定型文が返ります。

今日はたくさん質問してくれてありがとう！ちょっと休憩して、1時間ほどしてからまた質問してね :relaxed:
項目内容
単位生徒ごと（チャンネルごとではない）
判定タイミングLLM を呼ぶ前。超過ぶんは課金されません
数え方直近 1 時間に成功した回答の件数。スレッド要約や内部処理はカウントされない
記録/admin/errors に RATE_LIMITED（深刻度 情報）。既定のフィルタでは表示されない
解除自動。1 時間のスライド窓なので、古い質問が窓から外れれば再び使える
変更したい場合src/shared/lib/constants.ts の RATE_LIMIT_QUESTIONS_PER_HOUR を変更 → 再デプロイ（コード変更）

「生徒から『使えない』と言われた」ときは、まずこれを疑ってください。 /admin/errors の深刻度フィルタを すべて にして RATE_LIMITED を探します。

9-3. ジョブ管理（/admin/jobs）の見方

生徒の質問は 1 件ずつ「ジョブ」として処理されます。この画面は詰まりを見つける場所です。

3 つの KPI

カード正常滞留しているときの意味
待機中
登録からの最長待ち時間		滞留なし 受け付けたが処理が始まっていない。数分で消えるなら正常な通過状態。15 分以上残るならバックグラウンド実行が起動していない
処理中
実行開始からの最長経過		滞留なし 処理が始まったまま終わっていない。10 分以上は異常（関数のタイムアウト・プランの実行時間上限を疑う）
失敗
最も古い失敗からの経過		滞留なし 回答できなかった質問がある。生徒は待ちぼうけです。最優先で対応する

スイープ（滞留ジョブの回収）

このアプリは Cron を使いません。代わりに この画面を開いたときに自動で回収処理が走ります（60 秒に 1 回まで）。 手動で走らせたいときは スイープ実行 ボタンを押してください。

スイープがやること基準
処理中 のまま固まったジョブを 失敗 にする開始から 10 分超過
待機中 のまま放置されたジョブを 失敗 にする登録から 15 分超過
古いジョブ記録を削除完了系のみ 7 日経過
古い Slack イベント受信記録を削除30 日経過

回収して 失敗 にしても、生徒には何も通知されません （すでに回答が届いている可能性があり、二重に案内すると混乱するため）。滞留を見つけたら人が判断します。

失敗ジョブの再実行

失敗 の行にだけ 再実行 ボタンが出ます。押すと確認ダイアログが表示されます。

ダイアログの文言意味コスト
生成済みの回答が残っているため、AI を呼び直さず Slack への投稿だけをやり直します。 回答は作れていたが Slack への投稿で失敗したケースかからない
AI 回答を生成し直して Slack に投稿します（API 利用コストが発生します）。 回答生成そのものが失敗したケースかかる

二重返信ガード: 再実行の直前に「同じスレッドに Bot の返信がすでにあるか」を必ず確認します。 配信済みなら実行せずに完了として記録し、既に回答が配信済みのため再実行せず、完了として記録しました（二重返信の防止） と表示されます。 安心して押して構いません。誤って同じ回答が 2 回投稿されることはありません。

9-4. エラー対応フロー（/admin/errors）

1 日 1 回、朝に開くのを習慣にしてください。ダッシュボードの 未対応エラー の数字が入口です。

手順

  1. /admin の 未対応エラー が 0 なら何もしなくてよい
  2. 1 以上なら エラー管理を開く → をクリック（未対応で絞り込まれた状態で開く）
  3. エラーコードをクリックして詳細を見る
  4. 下の表で対応を判断する
  5. 対応が終わったら 対応済みにする。何をしたかを 対応メモ に残す
コード意味やること緊急度
AI_RESPONSE_FAILEDLLM 呼び出しの失敗「内部エラー詳細」を確認。API キーの失効・残高切れ・モデル名の誤りが典型。連続するなら緊急停止して調査高
AI_RATE_LIMITEDプロバイダ側の 429（生徒のレート制限ではない）自動リトライされる（5秒→15秒→45秒）。頻発するならプランの引き上げか、モデル変更を検討中
AI_TIMEOUT / JOB_TIMEOUT生成に時間がかかりすぎた単発なら様子見。頻発するならモデルを軽いものに変更中
SLACK_POST_FAILEDSlack への投稿に失敗Bot がチャンネルから外されていないか確認。/invite し直す高
SLACK_FILE_DOWNLOAD_FAILED画像の取得に失敗単発なら Slack 側の一時障害。頻発するなら files:read スコープを確認低
CHANNEL_NOT_BOUND紐付けの無いチャンネルでメンションされた正当なチャンネルなら紐付けを登録。無関係なら Bot を退出させる低
UNSUPPORTED_FILE_TYPE / IMAGE_TOO_LARGE生徒の操作ミス生徒に伝え方を案内（画像は jpg/png、20MB 以下）低
THREAD_SUMMARY_FAILED / EVALUATOR_FAILED回答後の内部処理の失敗回答自体は生徒に届いている。頻発しなければ無視してよい低

既定では エラー・警告 のみ表示されます。RATE_LIMITED や重複イベントなどの 情報 レベルは、深刻度フィルタを すべて にしたときだけ見えます（正常動作の記録なので普段は隠されています）。

9-5. 退塾・休塾時の処理

生徒を削除しないでください。会話ログ・レポート・利用実績が紐付いており、 消すと過去の記録が追えなくなります。「無効」にするのが正しい手順です。

手順

  1. 生徒管理 → 対象の生徒を開く
  2. ステータス を 無効 に変更 → 保存
無効にすると挙動
Bot の応答完全に沈黙する。メンションしても何も返さない（案内文も出さない）
集計ダッシュボードの生徒数・各種集計から除外される
選択肢レポート作成・チャンネル紐付けの生徒選択肢に出なくなる
記録残る。生徒一覧・会話ログ・レポートからは引き続き参照できる
ログ質問が来ると PERSON_INACTIVE（情報 レベル）が記録される

Slack のチャンネル自体はアーカイブしておくと、生徒側にも「終わった」ことが伝わります。 復塾したら有効に戻すだけで元通り動きます。

チャンネルだけ止めたい場合

生徒は在籍したままチャンネルの Bot だけ止めるなら、チャンネル設定 → 該当行 → ステータス を 無効 に。 この場合は「まだ設定が完了していない」という案内文が返るようになります。

9-6. 月次のコスト確認

頻度やること見るところ
毎日未対応エラーの確認/admin のダッシュボード
毎週質問数の推移に異常な跳ねが無いか/admin/usage の 日別 質問数（7日）
毎月推定コストと実請求の突き合わせ/admin/usage（30日）+ プロバイダの請求ページ
モデル変更時MODEL_PRICING の更新src/shared/lib/constants.ts

管理画面のコストは「推定値」です。アプリ内の単価表から計算しているので、次のズレが出ます。

  • 単価未登録のモデルは $0.00 になる（トークン数は正しく記録される）→ STEP 1
  • Embedding のコストは含まれない（LLM 呼び出しのみ記録）
  • プロバイダが単価を改定しても自動では追随しない

月に一度はプロバイダの請求額を正として突き合わせ、乖離が大きければ単価表を更新してください。

コストが急に増えたときの調べ方

  1. /admin/usage → 日別 コスト でいつから増えたかを特定
  2. 生徒別 質問数（上位10） で特定の生徒に偏っていないか確認
  3. モデル別 利用回数 で意図しない高額モデルが使われていないか確認
  4. 異常なら 緊急停止してから原因を調べる

9-7. バックアップ

Free プランには自動バックアップがありません。 生徒の会話ログ・プロフィール・レポートが消えたら復旧できません。 週 1 回の取得を運用の必須作業として担当と曜日を決めてください。

よくある誤解: supabase db dump は既定でスキーマ（テーブル定義）だけを出します。 --data-only を付けないと生徒のデータは 1 行も入りません。 「ファイルはできているのに中身が無い」という最悪の勘違いを避けるため、下の scripts/backup-db.sh を使ってください（3 本まとめて取り、中身の検査までします）。

週次の取り方

接続文字列は Supabase Dashboard → Project Settings → Database → Connection string の Session pooler（...pooler.supabase.com:5432）を使います。

SUPABASE_DB_URL='<Session pooler の接続文字列>' ./scripts/backup-db.sh
  • 出力はリポジトリの外（既定 ../juku-ai-backups/）。 公開リポジトリに個人情報を置かないため、リポジトリ内を指定すると実行を拒否します
  • 失敗すると非ゼロ終了し、途中まで出たファイルは捨てます。 「テーブルが揃っていない」「データが 0 件」のダンプも失敗扱いです
  • 同時に出る ...-MANIFEST.txt にはテーブルごとの行数が入ります。 捨てずに保管してください（復元できたかの判定に使います）

取れているだけでは不十分です。 四半期に 1 回、実際に空の DB へ復元して戻ることを確認してください。 手順と判定基準は docs/03_技術設計/09_バックアップとリストア.md、 判定用のクエリは scripts/restore-verify.sql にあります。

対象方法頻度
DB（生徒・レポート・会話ログ） ./scripts/backup-db.sh（roles / schema / data の 3 本 + MANIFEST）
Free プランに自動バックアップは無いので、これが唯一の防波堤です		 週次
手動スナップショット 大きな変更（一括登録・migration 追加）の前に、同じスクリプトを回す 都度
リストア訓練 ダンプから空の DB へ復元し、scripts/restore-verify.sql で行数・RLS・RAG を確認 四半期
添付画像 Storage の attachments バケット。DB のダンプには実ファイルが入りません （メタデータの行だけ）。重要なら Dashboard から手動ダウンロード 任意
環境変数 Vercel の設定値一式をパスワードマネージャに控える。 プロジェクトを作り直すときに一番困るのがこれ 変更時
コード GitHub。MODEL_PRICING を編集したら必ずコミットする 変更時
