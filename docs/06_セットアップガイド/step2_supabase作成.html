STEP 2 — Supabase プロジェクト作成

DB・認証・画像ストレージをまとめて担当する Supabase を用意します。 このステップの山場は「サインアップの無効化」です。これを忘れると、誰でもアカウントを作れて生徒の個人情報にアクセスできる状態になります。

所要時間約 15 分（プロビジョニング待ち含む）
このステップで手に入るもの（控える）
  • Project URL（https://xxxx.supabase.co）
  • anon public key
  • service_role key
  • DB パスワード
  • Project Ref

2-1. プロジェクトを作成する

  1. Supabase ダッシュボード → New project
  2. Organization は塾ごとに分けるか、自分の Organization 配下に作るかを決める（請求単位になります）
  3. 入力項目:
項目設定値理由
Name<塾名>-jukuaiあとで複数塾を運用したときに識別できるように
Database Password自動生成のものをそのまま使うこの画面を閉じると二度と見られません。必ずメモ（STEP 3 の db push で使います）
RegionNortheast Asia (Tokyo)塾も生徒も日本国内。DB のレイテンシは 1 質問で何度も効いてくる
Postgres Version17（選択肢があれば最新の 17 系）migration は 17 系で動作確認済み。pgvector も同梱
PlanProSTEP 1-4 の理由（自動停止しない・ストレージ・バックアップ）

作成後、プロビジョニングに 2〜3 分かかります。緑色の「Project is ready」になるまで待ちます。

Project Ref を控える: ダッシュボードの URL https://supabase.com/dashboard/project/<ここが Project Ref> の部分です。 Project URL https://<Project Ref>.supabase.co と同じ文字列で、STEP 3 の supabase link --project-ref に使います。

2-2. API キー 3 種を取得する

Project Settings（歯車）→ API を開きます。

ダッシュボード上の名前控える環境変数名公開範囲注意
Project URL NEXT_PUBLIC_SUPABASE_URL 公開して OK
（ブラウザに埋め込まれる）		 末尾のスラッシュは付けない。https:// から始まる URL 形式でないと起動時のバリデーションで落ちる
anon / public
（新しい UI では publishable）		 NEXT_PUBLIC_SUPABASE_ANON_KEY 公開して OK ブラウザ側ではログイン／ログアウトにしか使っていません。DB へは RLS のデフォルト拒否＋staff/admin 限定 SELECT でしか通りません
service_role
（新しい UI では secret）		 SUPABASE_SERVICE_ROLE_KEY 最重要機密 RLS を完全にバイパスします。絶対に NEXT_PUBLIC_ を付けない。Slack・チャット・スクショに貼らない

SUPABASE_SERVICE_ROLE_KEY が漏れると、全生徒の氏名・保護者メール・会話ログが読み書きし放題になります。 このキーはサーバー（Vercel の環境変数）にだけ置き、ローカルの .env.local は .gitignore 済みであることを確認してください。 漏洩が疑われる場合は Supabase ダッシュボードからキーをローテートし、Vercel の環境変数を更新して再デプロイします。

アプリ本体（Server Component / Server Action / Slack Webhook）は、すべて service_role クライアントで DB にアクセスします。 認可はアプリ側の requireStaff / requireAdmin と、Slack の channel_id → 生徒解決で担保する設計です。

2-3. 【必須】サインアップを無効化する

この作業を飛ばすと、RLS の強化（migration 026）が骨抜きになります。

026 で authenticated ロールに残しているのは 「app_metadata.role が staff または admin のときだけ許す SELECT」だけです。 セルフサインアップを許すと、誰でも authenticated にはなれてしまいます。 ロール未設定なら今は読めませんが、「素性の分からない認証済みユーザー」がいくらでも増える状態は、 ロール付与ミス 1 回で全生徒の PII 流出に直結します。招待制にしてください。

手順

  1. Authentication → Sign In / Providers
  2. Allow new users to sign up を OFF にする
  3. Save

migration 026_harden_rls_policies.sql のヘッダにも「運用上の必須手順」として同じことが書かれています: Supabase Dashboard > Authentication > Sign In / Providers で「Allow new users to sign up」を OFF にすること。

ではどうやって管理ユーザーを作るのか？ ダッシュボードから個別に追加します（STEP 7）。 Authentication → Users → Add user でメールとパスワードを入力し、Auto Confirm User にチェックを入れます。 その後 SQL で app_metadata.role を付与します。生徒は Slack 経由でしか触らないので、Auth ユーザーは作りません。

確認方法

STEP 5 のデプロイ後、https://<あなたのドメイン>/login にサインアップ用のリンクが無いこと、 かつ未登録メールでログインを試みても アカウントが作られないことを確認します （このアプリのログイン画面はメール + パスワードのみで、サインアップ UI は最初から存在しません）。

2-4. URL 設定

Authentication → URL Configuration:

項目値補足
Site URLhttps://<あなたのドメイン>STEP 5 で Vercel のドメインが確定してから設定（先に http://localhost:3000 でも可）
Redirect URLshttps://<あなたのドメイン>/**パスワードリセットのメールリンク用。使わないなら未設定でも動く

このアプリのログインは signInWithPassword（メール + パスワード）だけで、マジックリンクも OAuth も使っていません。 そのため URL 設定を間違えてもログイン自体は動きます。パスワードリセットを使う場合だけ正しく設定してください。

2-5. 【任意】メール送信の設定

Supabase の組み込みメール送信はレート制限が厳しく、パスワードリセットが届かないことがあります。 塾のスタッフが自分でパスワードを再設定できるようにしたいなら、Project Settings → Authentication → SMTP Settings でカスタム SMTP を設定してください。 設定しない運用（＝あなたがダッシュボードからパスワードを再発行する）でも問題ありません。
