## B. テスト面の制約 — 何を保証していないか

### OBS-01. staff の JWT では PostgREST から PII を読めない（設計より厳しい）

`e2e/acceptance/security-rls.spec.ts` の AT-11 が固定している挙動。

- migration `026_harden_rls_policies.sql` は staff/admin に SELECT ポリシーを作っている。
- しかし migration `024_fix_service_role_grants.sql`（GRANT 整理）で `authenticated` ロールから
  テーブル権限自体を剥奪している（残るのは TRUNCATE / TRIGGER / REFERENCES のみ）。
- **GRANT は RLS ポリシー評価より前に効く**ため、staff でも 403 `permission denied` になる。

**影響**: アプリ本体は Service Role で動くため機能影響なし。むしろ
「ブラウザに届く経路には PII が 1 行も出ない」ことが確定しており、**安全側のズレ**。

**運用上の注意**: Supabase Studio や REST で目視確認したい場合、staff アカウントの JWT では読めない。
Service Role キーを使うか、Studio の SQL Editor（Service Role で動く）を使うこと。
「権限があるはずなのに 403」で調査を始めると時間を溶かすため、ここに記録しておく。

**整合させるなら**: migration で `authenticated` に SELECT を GRANT し直す（1 行）。
ただし現状のほうが安全なので、必要になるまで変えない。

---

### OBS-02. Slack と LLM はすべてモック — 実 API を 1 回も呼んでいない

受け入れテスト 26 件と基礎 E2E 60 件、**86 件すべて** `e2e/acceptance/mock-server.mjs` に対して走っている。

| 保証している | 保証していない |
|---|---|
| Slack 署名（HMAC-SHA256 v0）の検証ロジック — 実アルゴリズムで生成した署名が通る | 実 Slack の **3 秒 ACK 制約**。ローカルはゼロレイテンシ |
| event_callback の**形状**に対する分岐（メンション / スレッド / `bot_id` / 未紐付け） | 実 Slack クライアントが送る実イベントでの動作 |
| Slack Web API を**呼ぶこと**と、渡すパラメータ | `chat:write` / `reactions:write` / `files:read` スコープの充足、Bot のチャンネル参加 |
| LLM を**呼ぶ / 呼ばない**の判断、プロンプトへの入力、出力のエスケープ・打ち切り通知 | 回答の**品質**、実レイテンシ、実トークン単価 |
| `ai_usage_logs` に model / tokens / latency が記録されること | `estimated_cost` の正しさ（モックモデルは `MODEL_PRICING` に無く 0 で記録される） |
| `#alerts` 通知メッセージの**組み立て**（種別・理由・操作者） | 実 `#alerts` チャンネルへの**着弾** |

→ すべて [`90_本番疎通チェックリスト.md`](90_本番疎通チェックリスト.md) に送っている。

**この設計を選んだ理由**: 受け入れテストが課金を発生させず、外部障害で落ちず、決定的に再現するため。
実 API を叩くテストは「落ちたときに自分のバグか相手の障害か分からない」ため、CI の信頼性を下げる。

### OBS-03. Vercel ランタイム固有の挙動は Playwright の射程外

ローカルは `pnpm exec next start`（常駐プロセス）で動いており、以下は**構造的に再現できない**。

| 項目 | ローカル | 本番（Vercel） |
|---|---|---|
| コールドスタート | 無し（常駐） | 発生する。初回リクエストが遅い |
| `maxDuration = 300` | 効かない（常駐プロセスは kill されない） | 5 分で関数が kill される |
| `after()` の実行保証 | プロセスが生きている限り完走 | 関数の寿命に縛られる |
| 滞留ジョブ | 発生しない（即座に完走する） | タイムアウトで `processing` のまま残りうる |

**結果**: `sweepStaleJobs()`（滞留ジョブの回収）と `retryJob()`（二重返信ガード付き再実行）は
**ユニットテストでしか検証されていない**（`sweepStaleJobs.test.ts` / `retryJob.test.ts`）。
実際に滞留したジョブが回収される様子は AT-P11 / AT-P14 で人が確認する。

### OBS-07. `AI_PAUSED` / `RATE_LIMITED` のエラー詳細が「返信なし」と誤表示する — **修正済み**

**受け入れテストの証拠スクリーンショット取得中に判明した表示上の不整合。** 挙動のバグではない。

> **対応済み（2026-08-02）**: 両方の `logError` 呼び出しに `userFacingMessage` を渡すよう修正し、
> エラー詳細画面に実際に返した定型文が表示されるようになった。
> 記録漏れの再発防止として、`processJob.test.ts` と `executeProcessMessage.test.ts` に
> `user_facing_message` / `userFacingMessage` の検証を追加している。
> **以下は発見時の記録**。掲載中の証拠スクリーンショットは修正前に取得したものなので、
> 「返信なし」表示が写っている点に注意（挙動は当時から正常）。

`/admin/errors/{id}` の「ユーザーへ返した文言」欄が
**「返信なし（サイレント処理されたエラーです）」**と表示されるが、
実際には両ケースとも生徒に定型文を返している。

| コード | 実際に返している文言 | 記録箇所 |
|---|---|---|
| `AI_PAUSED` | 「いまメンテナンス中でお返事ができないんだ…」 | `src/features/jobs/lib/processJob.ts` |
| `RATE_LIMITED` | 「ちょっと休憩して、1時間ほどしてからまた質問してね」 | `src/features/jobs/lib/executeProcessMessage.ts` |

**原因**: どちらも `postMessage()` で定型文を送った直後に `logError()` を呼んでいるが、
`logError` に `userMessage` を渡していない。渡していない場合の表示が「返信なし」になる。

**影響**: 生徒への返答は正常（AT-40 / AT-44 でモック Slack へのアサーション済み）。
影響を受けるのは**管理画面の表示だけ**。ただし運用者が
「生徒には何も届いていない」と誤解し、不要な個別フォローをする可能性がある。

**回避策（運用）**: `AI_PAUSED` と `RATE_LIMITED` は**定型文が届いている**と読み替える。
両コードとも severity は `info`（正常動作の記録）であり、対応不要。

**直すなら**: 上記 2 箇所の `logError` に `userMessage: getUserFacingMessage(code)` を渡す（各 1 行）。
今回はレポート作成のスコープ外としたため未修正。

## C. テストで検証できない運用前提

自動テストにも本番疎通確認にも現れないが、**設定を誤ると防御が無効化される**もの。

| # | 前提 | 誤るとどうなるか | 確認場所 |
|---|---|---|---|
| 1 | Supabase の「Allow new users to sign up」が **OFF** | 誰でもアカウントを作れる。ただしアプリ層の `requireStaff` が role を検証するため管理画面には入れない（AT-05 で検証済み）。多層防御の 1 枚目が抜ける状態 | セットアップガイド STEP 2 / `90_` §0 |
