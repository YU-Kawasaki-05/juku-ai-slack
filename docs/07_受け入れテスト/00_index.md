## 3. 特筆事項 — 受け入れテストが検出した公開ブロッカー（AT-05）

**発見 → 修正済み。** 経緯を残す。

当初、**「Supabase Auth にサインアップできただけで role を持たないユーザーが、
管理画面から全生徒の PII（氏名・学年・質問本文）を閲覧・編集できる」**状態だった。

なぜ通ってしまっていたか:

1. migration `026_harden_rls_policies.sql` で RLS を強化したが、これが塞ぐのは **PostgREST 直アクセスだけ**。
2. 管理画面は **Service Role で DB に接続するため RLS を迂回する**。
3. 当時の `requireStaff()` は「認証されているか」しか見ておらず、`app_metadata.role` を検証していなかった。

**自動テストの設計（ロールを持つユーザーでの操作）では出ず、
「権限を持たない人の視点で実際に操作する」受け入れテストだから見つかった**類の欠陥。

修正（W5-A）:

- `requireStaff` / `requireStaffPage` が `app_metadata.role ∈ {staff, admin}` を厳密比較で検証する
- `user_metadata` は判定に一切使わない（本人が書き換えられるため）
- 未認証（unauthorized）と権限なし（forbidden）を分離し、後者は専用ページ **`/admin/no-access`** に案内
- `no-access` は `(no-shell)` ルートグループに置き、`admin/layout.tsx` の認可継承を外してリダイレクトループを回避

現在 AT-05 は「**ログインは通るが `/admin/no-access` に着地し、`/admin/persons` を直接叩いても
生徒名が 1 件も描画されない**」ことを検証するリグレッションテストとして機能している。
証拠: [`evidence/AT-05_ロールなしユーザーは管理画面を利用できない.png`](evidence/AT-05_ロールなしユーザーは管理画面を利用できない.png)

併せて AT-05b（`user_metadata` 自称での昇格不能）、AT-B06 / AT-B07（**正当な staff を締め出していない**ことの逆検証）を対で配置した。

## 4. Slack フルフロー（AT-30 系）で通したもの

署名付き `event_callback` の受信から、回答の Slack 投稿と会話ログ記録までの**全経路**を 11 ケースで通している。

```
署名付き POST → 署名検証 → ACK 200 {ok:true} → after() で
  紐付け解決 → jobs 積み込み → 🤔 付与 → プロンプト構築 → LLM →
  出力エスケープ → chat.postMessage → 🤔 除去 → slack_messages / ai_usage_logs 記録
```

**本物**: Slack 署名（実 HMAC-SHA256 v0）・event_callback のペイロード形状・ACK・ジョブ状態遷移・
DB（ローカル Postgres）・プロンプト構築・出力エスケープ・利用量記録

**モック**: Slack Web API（`chat.postMessage` / `reactions.add` / `reactions.remove`）・LLM（OpenAI 互換）

確認できたこと: 正常系フルフロー（AT-30）/ 冪等性（AT-31）/ 未紐付けの案内（AT-32）/
直下メンション必須（AT-33）/ 退塾生の沈黙（AT-34）/ 通知インジェクションのエスケープ（AT-35）/
打ち切り通知（AT-36）/ スレッド追撃（AT-37）/ Bot 自身の無視（AT-38）/
障害時の情報漏洩なし（AT-39）/ 利用量記録（AT-47）

**LLM を呼ばない**ことが要件のケース（AT-32 / AT-33 / AT-34 / AT-38 / AT-40 / AT-44）は、
文言だけでなく**モック LLM への呼び出しが 0 件であること**まで確認している。

## 5. 公開可否の所見

### 結論

**自動テストで検証できる範囲では、公開を止める欠陥は残っていない。**
必須ケース 37/37 が通過し、当初検出した公開ブロッカー（AT-05）は修正済み。
ただし**このレポートだけでは公開可否を判定できない**。下記の条件が付く。

### 判定の根拠（確認できたこと）

| 観点 | 状態 |
|---|---|
| PII の保護（DB 層） | anon key / ロールなし JWT / staff JWT のいずれでも、保護 7 テーブルから 1 行も読めない |
| PII の保護（アプリ層） | role なしは `/admin/no-access` へ。`user_metadata` 自称でも昇格不能 |
| 権限分離 | staff は Embedding 再生成・チャンネル紐付け・kill_switch 切替を実行できない。かつ**閲覧は妨げられていない** |
| 中核機能 | Slack フルフローが端から端まで通り、会話ログに残る |
| コスト遮断 | 全停止（kill_switch）と生徒単位制限（10 問/時）の両方で、LLM 呼び出しが 0 件になることを確認 |
| 障害時の挙動 | 内部情報を漏らさず、運用側は `/admin/errors` で原因を追える |
| 静的品質 | tsc clean / eslint clean / ユニット 717 pass |

### 公開の条件（これが埋まるまで「可」とは言えない）

1. **[`90_本番疎通チェックリスト.md`](90_本番疎通チェックリスト.md) の必須 12 項目を実 Slack で消化すること。**
   自動テストは 86 件すべてモック Slack + モック LLM に対して走っており、
   実 Slack の 3 秒 ACK・Vercel のコールドスタート・実 LLM の品質とコスト・
   Slack スコープの充足・画像添付・`#alerts` の実着弾は**一度も検証されていない**。
   とくに以下はサイレント失敗するため、人が見ないと気づけない:
   - `LLM_MODEL_COMPLEX` 未設定 → 画像がエラーも出さず無視される
   - `MODEL_PRICING` 未登録 → コストが `$0.00` のまま積み上がる

2. **運用前提の設定を確認すること**（`91_既知の制約.md` §C の 7 項目）。
   とくに Supabase の「Allow new users to sign up」を OFF にすること、
   `SUPABASE_SERVICE_ROLE_KEY` をクライアントに露出させないこと。

3. **手動レポート運用で開始することを関係者と合意していること。**
   FR-08（AI 月次レポート自動生成）と保護者メール通知は未実装（`91_既知の制約.md` A-1）。

### 併せて認識しておくべきこと（公開を妨げないが、伝えるべきもの）

- **FR-05 の socratic / confirmation モードは到達しない**（トピック検出が未実装のため常に direct）。
  学習支援としては direct でも成立するが、「対話的に導く AI」を期待されていると齟齬になる（`91_既知の制約.md` A-2）。
- **外部 APM は未導入**。障害検知は日次で `/admin/errors` と `/admin/jobs` を目視する運用に依存する（同 A-3）。
- **`/admin/errors` の表示の不正確さ（OBS-07）は修正済み**。`AI_PAUSED` / `RATE_LIMITED` の詳細ページで
  「ユーザーへ返した文言」が「返信なし」と出ていたが、`logError` に実際の文言を渡すよう修正し、
  再発防止のテストも追加した。**掲載中の証拠スクリーンショットは修正前に取得したもの**のため
  「返信なし」が写っている（挙動は当時から正常）。
- **Vercel Pro プランが事実上必須**（`maxDuration = 300` のため）。
