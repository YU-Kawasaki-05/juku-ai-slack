## このカテゴリの位置づけ

ここは**基礎 E2E（`e2e/` 直下）が全面的に担保している**領域で、受け入れテスト専用 spec は置いていない。
理由は、管理画面の CRUD が「壊れたら即座に気づける」性質を持つのに対し、
受け入れテスト spec は「壊れても気づけない」もの（権限の穴・コスト遮断・外部連携）に集中させたため。

ただし引き渡し判断には CRUD の状態も必要なので、**基礎 E2E の内容をケースとして棚卸しし、結果を記載する**。
すべて同じ実行（86 pass）に含まれる。

**認証は admin の `storageState` を使用**（`e2e/global-setup.ts` がテストユーザーを作成し保存）。
staff 視点の権限境界は `10_認証認可.md` の AT-B04〜AT-B07 を参照。

## AT-B17 レポート（下書き → Embedding 警告 → 承認）

**優先度**: 必須 / **実施方法**: 基礎 E2E（Playwright 3 テスト）/ **要件**: FR-16 / DEC-14 / BR-16-03 / H-2

### 手順と期待結果

| # | 手順 | 期待 |
|---|---|---|
| 1 | 生徒・対象月・タイトル・本文を入力 → 「下書き保存」 → 詳細を開く → 「編集」 → 「承認して保存」 | 一覧で「下書き」→ 詳細に「Embedding 再生成が必要です」警告 +「未生成」表示 → 承認後は一覧で「承認済み」 |
| 2 | タイトル入力欄で **Enter** を押す | 承認されず**下書き保存**になる（一覧行が「下書き」で「承認済み」を含まない） |
| 3 | 同じ生徒・同じ月でもう 1 件作成 | 「この生徒のこの月のレポートは既に存在します」 |

### 実結果

PASS（3/3）。

### 補足

#1 の Embedding 警告は「E2E 環境に `EMBEDDING_*` を設定していないため保存時の自動生成が必ず失敗する」ことを利用して、
**DEC-14 の警告経路**を確実に踏ませている。つまりこのケースが検証しているのは
「Embedding が生成されること」ではなく「**生成に失敗したことが画面で分かること**」。
実際の Embedding 生成は本番環境の設定に依存する。

#2 は H-2 対策。フォーム内で Enter を押すと最初の submit ボタンが発火する HTML の既定挙動により、
**未完成のレポートが誤って承認される**事故を防ぐ。

## AT-B18 ジョブ管理

**優先度**: 推奨 / **実施方法**: 基礎 E2E（Playwright 3 テスト）/ **要件**: FR-04 / F-4 / A-14 / DEC-13

### 背景

Cron を使わない運用（DEC-13）なので、**この画面を開くこと自体が滞留ジョブの回収トリガー**になっている。
日次で開く運用が Runbook（`docs/03_技術設計/06_運用設計.md` S-04）に定められている。

### 手順と期待結果

| # | 手順 | 期待 |
|---|---|---|
| 1 | `/admin/jobs` を開く | h1「ジョブ管理」+ KPI カード「待機中」「処理中」「失敗」+ 説明文「この画面を開くと滞留ジョブの回収と古い記録の掃除を自動実行します」 |
| 2 | 「スイープ実行」 | トースト「滞留ジョブを N 件回収、古い記録を M 件掃除しました」（**0 件でも成功する**こと） |
| 3 | 「状態」→「失敗のみ」→「クリア」 | URL に `status=failed` + 件数サマリー「表示中 N 件 / 失敗のみ」→ クリアで戻る |

### 実結果

PASS（3/3）。

### 保証しないこと

**実際に滞留したジョブが回収されること**は、本番の関数タイムアウト（`maxDuration=300`）を跨がないと再現できない。
ローカルではジョブは即座に完走するため、スイーパの効果はユニットテスト
（`sweepStaleJobs.test.ts` / `retryJob.test.ts`）とAT-P11 / AT-P14 に委ねている。
